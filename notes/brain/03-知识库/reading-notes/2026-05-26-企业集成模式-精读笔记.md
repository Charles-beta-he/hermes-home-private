## 10 条关键概念 / examples

1. **Messaging as decoupling**：消息把发送方和接收方在时间、位置、实现上解耦；代价是需要显式处理顺序、重复、失败和可观测性。
2. **Message Channel**：通道是语义边界，不只是队列名；命名应表达业务事件/命令或数据类型，避免让消费者猜含义。
3. **Point-to-Point vs Pub/Sub**：点对点适合一个消费者处理一个工作单元；发布订阅适合多个独立投影/副作用监听同一事实。
4. **Message Router**：路由把“决定谁处理”从生产者中抽离；适用于按内容、租户、版本、地域或能力分发。
5. **Message Translator / Canonical Data Model**：跨系统集成的长期成本往往在格式/语义转换；规范化模型可降低 N×M 转换爆炸，但会形成中心模型治理负担。
6. **Request-Reply + Correlation Identifier**：异步请求响应必须能把 reply 关联回 request；相关 id 是可靠链路追踪、幂等和超时恢复的基础字段。
7. **Splitter + Aggregator**：把复合消息拆分并发处理后再聚合，必须定义完成条件：计数、超时、水位线、业务闭包或补偿策略。
8. **Idempotent Receiver**：消息系统默认可能重复投递；接收端应以业务幂等键、去重表或状态机防止重复副作用。
9. **Dead Letter / Invalid Message Channel**：坏消息不要阻塞主线；应分流到可审计队列，并记录错误类型、原始元数据、重放条件。
10. **Wire Tap / Message History / Message Store**：消息链路的调试能力不是附加功能；没有旁路观察、历史轨迹和可重放存储，分布式集成会退化为黑盒排障。

## 3 个实践练习

1. **订单事件拓扑练习**：设计 `OrderPlaced` 的 Pub/Sub 拓扑：库存预占、邮件通知、风控、数据仓库分别作为独立消费者；写出每个消费者的幂等键与失败重试策略。
2. **异步 Request-Reply 练习**：为“生成报表”设计请求消息、reply channel、correlation id、超时和取消语义；说明 UI 如何查询状态而不是阻塞等待。
3. **Splitter/Aggregator 练习**：把“批量同步 1000 个客户资料”拆成单客户消息；定义聚合器的成功/部分失败输出、超时阈值和 dead-letter 重放流程。

## 可落地到 Hermes / 技能树的应用点

**Taskpool / Hermes 控制面可借鉴 EIP 的消息拓扑语言**：

- 把 task lifecycle event 视作消息：`task_added`、`claimed`、`running`、`review`、`blocked`、`done`。
- 为 follow-through / autorun / multimodel / dashboard 各自定义显式 channel，避免一个脚本同时承担路由、转换和执行。
- 给每次 dispatch tick 生成 correlation id（已有 run_id / tick id 可承担），并把 claim、worker、evidence、proof-check、dashboard 刷新串成 Message History。
- 对失败 worker 使用 Dead Letter Channel 风格：分类 `human_escape_triggered`、`proof_gate_failed`、`timeout`、`provider_unavailable`，并定义可重放条件，避免长期 claimed/running 黑洞。
- 对 advisory reading lane 使用 Message Store：笔记 artifact + task proof log + evidence frontmatter 三处互相指向，保证可检索和可审计。
