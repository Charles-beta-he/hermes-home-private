## 章节地图 / Chapter map

### 第1章 简介

1. 历史与发展：Redis 从高性能内存数据库演进为支持缓存、计数器、队列、会话、实时榜单与消息分发的通用基础设施。
2. 特性：围绕存储结构、内存存储与持久化、功能丰富、简单稳定，建立“为什么 Redis 值得学”的认知起点。

### 第2章 准备

3. 安装与启动：覆盖 POSIX / OS X / Windows 安装，启动/停止 Redis，说明学习与运维的最小环境准备。
4. CLI / 配置 / 多数据库：通过命令行、返回值、配置文件与逻辑数据库切分，让读者先具备实验与调参能力。

### 第3章 入门

## 10 条关键概念 / examples

1. **Redis 的核心价值不是“快”这么简单，而是“用少量数据结构覆盖大量业务模式”**：目录把五大类型放成全书最大基础篇幅，说明作者强调的是建模能力，而不是把 Redis 当成黑盒缓存。
2. **字符串是最通用的控制面数据结构**：计数器、缓存值、分布式锁标志、简单状态位都可以落在字符串；适合从最小状态机入门。
3. **散列最适合对象局部更新与字段化存储**：相比整块 JSON/字符串覆盖，散列更利于用户资料、配置项、统计字段等细粒度读写。
4. **列表、集合、有序集合分别对应“顺序流”“去重关系”“带权排名”三种高频场景**：任务队列/消息缓冲、标签/好友关系、排行榜/延时任务，本质上是不同业务语义的数据结构映射。
5. **WATCH + MULTI/EXEC 代表 Redis 的乐观并发控制思路**：它不是传统 SQL 事务替代品，而是更接近“先监视，后原子提交”的 CAS 风格更新。
6. **过期时间不是缓存配角，而是访问频控、时效状态和自动回收的主工具**：目录直接给出两个访问频率限制实现与缓存实现，说明 TTL 是业务规则的一部分。
7. **管道优化的是网络往返，不是命令语义**：当命令本身无需依赖上一步返回值时，pipeline 能显著减少 RTT；但它不自动提供 Lua 那种脚本原子性。
8. **Lua 脚本的核心价值是“把多步判断与修改合并到服务器端原子执行”**：访问频率限制示例就是典型用法，既降低网络开销，也避免客户端并发竞态。
9. **持久化要按故障模型选，不存在绝对最优**：RDB 更偏快照恢复与性能，AOF 更偏命令级可追溯与较强数据安全；实际生产常常组合使用。
10. **复制、Sentinel、Cluster 是三个不同层级的问题域**：复制解决副本与读扩展，Sentinel 解决高可用切换，Cluster 解决分片与水平扩展；把三者混为一谈会导致错误架构决策。

## 3 个实践练习

1. **练习 A：用五大类型重建一个真实业务模块**
   - 选择一个当前项目功能（如登录态、短信验证码、搜索建议、在线客服排队、热门榜单），分别说明用字符串/散列/列表/集合/有序集合中的哪一种或哪几种实现。
   - 交付：1 张“需求 → 数据结构 → 关键命令 → TTL/一致性策略”映射表。
   - 验收：至少比较 2 种备选结构，并说明为什么最终结构更匹配读写模式。

2. **练习 B：实现一个限流器并比较两种方案**
   - 方案 1：INCR + EXPIRE；方案 2：Lua 脚本一次性完成检查与递增。
   - 交付：列出并发竞态、失败模式、接口返回码与压测观察点。
   - 验收：能解释为什么方案 2 在高并发下更稳，以及它带来的脚本维护成本。

3. **练习 C：为一个生产缓存设计持久化与高可用策略**
   - 假设你要给用户会话 / 配置中心 / 推荐榜单三种场景选 Redis 部署方案，分别判断是否需要 AOF、是否需要副本、是否需要 Sentinel 或 Cluster。
   - 交付：一页决策表，列出恢复时间目标、可接受丢数窗口、读写比例和容量扩展方式。
   - 验收：能清楚区分“副本”“自动故障转移”“分片扩容”三类需求，不混用术语。
