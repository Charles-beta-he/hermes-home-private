## 章节地图 / Chapter map

### Part I. The Narratives（架构叙事主线）

1. **Layering**：解释企业应用为什么要分层，尤其是展示层、领域层、数据源层三大主层，以及这些层应当部署在何处。
2. **Organizing Domain Logic**：围绕“如何组织业务逻辑”做路线选择，对比不同组织方式，并引出 Service Layer。
3. **Mapping to Relational Databases**：说明对象模型与关系数据库之间的张力，以及行为映射、结构映射、关系映射、继承映射、元数据映射与数据库连接等问题域。
4. **Web Presentation**：讨论视图模式与输入控制器模式，建立 Web 界面的职责边界。
5. **Concurrency**：从并发问题、执行上下文、隔离性、乐观/悲观并发控制、事务与 ACID，到 offline concurrency 的前置理解。
6. **Session State**：强调无状态价值，并比较几种会话状态存储方式。
7. **Distribution Strategies**：讨论为什么分布式对象有诱惑也有代价，如何处理远程/本地接口与分发边界。
8. **Putting it all Together**：把领域层、数据源层、展示层与技术选型重新串起来，说明不同模式组合时的落地顺序。

### Part II. The Patterns（模式库）

9. **Domain Logic Patterns**：Transaction Script、Domain Model、Table Module、Service Layer。
10. **Data Source Architectural Patterns**：Table Data Gateway、Row Data Gateway、Active Record、Data Mapper。
11. **Object-Relational Behavioral Patterns**：Unit of Work、Identity Map、Lazy Load。
12. **Object-Relational Structural Patterns**：Identity Field、Foreign Key Mapping、Association Table Mapping、Dependent Mapping、Embedded Value、Serialized LOB、各类继承映射。
13. **Object-Relational Metadata Mapping Patterns**：Metadata Mapping、Query Object、Repository。
14. **Web Presentation Patterns**：MVC、Page Controller、Front Controller、Template View、Transform View、Two Step View、Application Controller。
15. **Distribution Patterns**：Remote Facade、Data Transfer Object。
16. **Offline Concurrency Patterns**：Optimistic Offline Lock、Pessimistic Offline Lock、Coarse-Grained Lock、Implicit Lock。
17. **Session State Patterns**：Client Session State、Server Session State、Database Session State。
18. **Base Patterns**：Gateway、Mapper、Layer Supertype、Separated Interface、Registry、Value Object、Money、Special Case、Plugin、Service Stub、Record Set。

## 10 条关键概念 / examples

1. **企业应用的核心难点不是语法，而是复杂业务规则的可驯化**：Fowler 在官方页以租赁系统为例，强调真正的难题来自“业务规则变化多、例外多、跨事务链路长”，而模式的价值是让复杂性变得可组织、可沟通。
2. **三层主结构是认知与职责分离工具，不只是部署习惯**：目录中 Layering 明确三大主层。它的重点不是把代码机械分文件夹，而是把“展示变化”“业务规则变化”“持久化细节变化”切开，降低耦合传播。
3. **领域逻辑组织方式要按复杂度选型**：第 9 章并列 Transaction Script、Domain Model、Table Module、Service Layer，意味着作者并不主张一把梭哈；简单 CRUD 可能适合脚本式流程，复杂规则系统更适合领域模型。
4. **Service Layer 的作用是稳定应用边界，而不是把所有逻辑都塞到 Service**：目录把它既放在叙事篇也放在模式篇，说明它一方面是应用边界模式，另一方面必须与领域逻辑组织方式配合使用。
5. **对象-关系映射的真正问题是“双模思维冲突”**：第 3 章和第 10–13 章大量篇幅都在处理对象图与表结构的张力。模式不是炫技，而是用来控制 identity、关系、继承、装载时机和查询复杂度。
6. **Data Mapper 与 Active Record 代表两种不同的复杂度立场**：目录并列这两个模式，说明一个偏“领域对象与存储彻底分离”，另一个偏“对象自带持久化行为”。团队选型要看业务复杂度和对象纯度诉求。
7. **Lazy Load / Identity Map / Unit of Work 是性能、正确性、开发体验的三角平衡**：它们都属于 ORM 行为模式，分别对应“何时加载”“同一对象是否唯一”“何时统一提交变更”，是企业应用性能与一致性的关键杠杆。
8. **Web 展示模式不是前端专属，而是服务端页面/接口编排的职责设计**：MVC、Page Controller、Front Controller、Application Controller 等模式帮助团队区分请求入口、页面装配与业务协调逻辑，避免路由、模板、业务规则相互污染。
9. **分布式边界要显式压缩聊天式调用**：Remote Facade 和 DTO 被单列成分布式模式，表明跨进程调用与本地调用成本完全不同；远程边界应粗粒度、可批量、可序列化，而不是把本地对象接口直接暴露出去。
10. **Offline Concurrency 说明“事务结束后世界还在继续变化”**：乐观锁、悲观锁、粗粒度锁、隐式锁都是在处理“用户跨多个请求/页面/时段完成一项业务操作”时的数据一致性问题，这对订单、审批、支付、配置后台尤其关键。

## 3 个实践练习

1. **练习 A：为现有后端模块判型领域逻辑模式**
   - 任选一个当前项目模块（如订单、资费、KYC、权限），判断它更接近 Transaction Script、Domain Model、Table Module 还是 Service Layer + Domain Model 组合。
   - 交付：写出“为什么这样判型”的 1 页说明，标明主要业务规则位于 Controller / Service / Domain / Repository 哪层。
   - 验收：能指出至少 2 个当前设计中的耦合点和 1 个更合适的模式迁移方向。

2. **练习 B：绘制一条对象到数据库的映射链**
   - 选择一个实际实体（如 User、Order、KycApplication），从对象属性、主键、外键、聚合关系、延迟加载点、更新提交时机六个维度梳理它的持久化路径。
   - 交付：1 张映射表，标明哪些地方当前更像 Active Record，哪些地方更像 Data Mapper。
   - 验收：能解释一个潜在的 N+1、脏写、重复对象或事务边界问题。

3. **练习 C：审视一个跨请求业务流的并发策略**
   - 选择一个需要用户多步操作的流程（如后台审批、支付确认、库存扣减、资料审核），判断应使用 Optimistic Offline Lock、Pessimistic Offline Lock 还是 Coarse-Grained Lock。
   - 交付：列出并发冲突场景、失败提示语和回退策略。
   - 验收：能说明为什么“数据库事务包住单个请求”仍不足以解决该业务冲突。

## 可落地到当前前端/后端/工程化能力的应用点

**把《企业应用架构模式》沉淀为 fullstack 架构分层与持久化边界审计基线。**

- 前端侧：以 MVC / Front Controller / DTO 思维审视 BFF、页面路由和接口编排，避免把业务规则散落在页面组件与请求封装中。
- 后端侧：用 Domain Logic Patterns + Repository/Data Mapper + Unit of Work 的视角复盘 Controller/Service/Entity/Repository 分层，识别“胖 Service、贫血 Domain、持久化细节泄漏到业务层”的问题。
