## 章节地图 / Chapter map

### 第一部分：Docker 深入解读

#### 第1章 从容器到容器云

1. 这章是全书问题定义：为什么云计算平台需要新的封装单元，为什么容器会成为继虚拟机之后的重要抽象。
2. 它把“容器”放到更大的平台演进里看，不只是一个打包工具，而是通向容器云的调度与交付基础。

#### 第2章 Docker 基础

3. 这一章聚焦上手与最短闭环：安装、常用参数、集群部署、Hello World，以及从开发到测试再到发布的一体化路径。
4. 它的作用不是教几个命令，而是建立 Docker 作为“应用栈交付单元”的基本心智模型。

#### 第3章 Docker 核心原理解读

5. 这是第一部分的技术中枢，覆盖 Linux namespace、cgroups、client/daemon、libcontainer、镜像、存储、数据卷、网络、安全。
6. 书的深度主要体现在这里：它要求读者从“会用 Docker”提升到“知道 Docker 为什么这样工作、瓶颈在哪里、风险在哪里”。

#### 第4章 Docker 高级实践技巧

7. 这一章把原理拉回工程实践：容器化思维、网络高级玩法、Dockerfile 最佳实践、监控、配置中心等，回答“生产里到底怎么用得更稳”。
8. 它说明容器化不是简单把应用塞进镜像，而是要重构日志、网络、配置、监控等配套治理面。

### 第二部分：Docker 云平台解读

#### 第5章 构建自己的容器云

9. 这一章是平台视角的转折点：从单机/单应用工具上升到云平台分层，讨论容器云建设的能力梯度。
10. “从小工到专家”意味着读者不仅要会部署，更要理解平台架构、角色分工与演进路径。

#### 第6章 专注编排与部署：三剑客与 Fleet

11. 本章围绕 Compose、Machine、Swarm、Fleet 展开，回答容器集群如何编排、宿主环境如何管理、调度策略如何工作。
12. 它对应的是“多容器、多主机、多环境”的复杂度爆炸问题，是从 Docker 工具走向平台能力的第一层跃迁。

#### 第7章 专注应用支撑和运行时：Flynn 和 Deis

13. 本章比较 Flynn 与 Deis 这类更靠近 PaaS/应用支撑层的容器云系统，关注的不只是容器调度，而是应用发布、运行时框架和平台功能面。
14. 它帮助读者区分“编排层”和“应用平台层”两类容器云路线，不把所有容器平台混成一个概念。

#### 第8章 一切皆容器：Kubernetes

15. 这是全书最长、最重的一章，从对象模型（Pod、RC、Service、ReplicaSet、Deployment、DaemonSet、ConfigMap、Job、HPA）一直讲到核心组件、存储、网络、多租户、认证授权、高级实践和未来方向。
16. 这章等于把 Kubernetes 作为“容器云操作系统”来讲，不止会用 YAML，而是理解控制面与数据面的整体设计。

### 第三部分：附录

17. 附录 A/F 分别补 Docker 和 Kubernetes 安装；附录 B/C 给源码阅读与开源项目熟悉方法；附录 D/E 深挖 cgroups 测试与参数。
18. 它们不是边角料，而是把“从使用到原理再到源码阅读”的学习链条补完整。

## 12 条关键概念 / examples

1. **容器不是终点，容器云才是本书真正的问题空间。** 第 1 章和第 5–8 章把单机容器工具上升为平台能力讨论。
2. **Docker 的价值在于把开发、测试、发布、部署收束到同一交付单元。** 第 2 章的应用栈与一体化流程就是这个闭环。
3. **理解 namespace 与 cgroups，才算真正理解容器。** 一个负责隔离，一个负责资源限制，它们共同构成容器抽象的内核基础。
4. **client/daemon 分离意味着 Docker 天生适合做远程控制与平台化封装。** 这也是后续集群化、编排化的结构前提。
5. **libcontainer/runC 是“容器如何真正落到内核上”的关键桥梁。** 不是所有复杂度都在 CLI，真正底座在 runtime 与内核交互。
6. **镜像、存储驱动、数据卷是三件不同但经常被混淆的事。** 镜像负责分发与分层，存储驱动决定读写机制，数据卷解决持久化与共享。
7. **网络与安全不是容器附属议题，而是落地时最容易出事故的主战场。** 第 3 章和第 4 章都给了它们很重的篇幅。
8. **Dockerfile 最佳实践本质上是在治理可重复构建与镜像质量。** 这直接关系 CI/CD、缓存命中、镜像体积与供应链可维护性。
9. **容器平台至少分两层：编排部署层与应用支撑层。** Compose/Swarm/Fleet 与 Flynn/Deis 的分章对比，正是在帮助读者建立这一分层。
10. **Kubernetes 把一切都对象化、控制器化。** Pod、Deployment、Service、Job、HPA 等对象共同构成声明式系统，而不是一组孤立命令。
11. **Kubernetes 的核心竞争力在组件协作与控制回路。** API Server、Scheduler、Controller Manager、Kubelet、Kube-Proxy 的配合，决定了它为何可扩展。
12. **学习容器技术不能停在“部署成功”。** 本书通过附录 B/C/D/E 明确强调源码阅读、cgroups 实验和开源项目熟悉方法，要求读者具备继续深挖的能力。

## 学习主线 / 推荐二刷顺序

1. 第一遍按书的顺序，先建立 `容器 -> Docker -> Docker平台化 -> Kubernetes` 的大图谱，不纠结每个实现细节。
2. 第二遍重点啃第 3 章和第 8 章，把 Docker runtime/镜像/网络/安全 与 Kubernetes 对象/控制面串成一条“原理主线”。
3. 第三遍按工程治理视角重排：Dockerfile、镜像分发、数据卷、网络、安全、监控、配置中心、认证授权、多租户、高可用。
4. 第四遍做技术比较卡片：Compose vs Swarm vs Fleet，Flynn vs Deis，Docker runtime 心智 vs Kubernetes control plane 心智。

## 4 个实践练习

1. **练习 A：手工搭建一个最小 Docker 应用栈并补全交付闭环**
   - 从一个熟悉的 Node/Java/前端静态服务开始，写 `Dockerfile`、`docker-compose.yml`，跑通 build / run / log / healthcheck。
   - 验收：本地一键启动；镜像可重复构建；应用日志不依赖 SSH 进容器排查。

2. **练习 B：做一次容器底层观察实验**
   - 用 `unshare`、`nsenter`、`docker inspect`、`cgroup` 相关命令观察 namespace 与资源限制的真实效果。
   - 验收：能说清 PID/NET/MNT namespace 与 cgroups 在一个容器实例上的具体体现。

3. **练习 C：为项目补一套镜像与运行治理规范**
   - 选当前项目的一条服务链路，补 Dockerfile 最佳实践、镜像分层策略、数据卷策略、监控指标与配置管理约束。
   - 验收：镜像构建时间、体积、环境一致性和可观测性均有明确改进点。

4. **练习 D：用 Kubernetes 对象模型重画一张业务部署图**
   - 选一个真实业务模块，画出 Pod、Deployment、Service、ConfigMap、Ingress/HPA（如适用）的映射关系，并解释控制流。
   - 验收：能说明请求怎么进来、配置怎么下发、实例怎么扩缩、故障如何恢复。

## 对当前前端/后端/工程化能力的可落地应用点

**把本书沉淀为“容器化交付 + 平台抽象 + Kubernetes 控制面”的统一学习骨架。**

- 对前端/全栈工程：第 2 章和第 4 章可直接迁移到前端 SSR、Node BFF、静态站点或 Java 服务的镜像化交付，重点是 Dockerfile、日志、配置与环境一致性。
- 对后端与基础设施协作：第 3 章和第 8 章有助于把“会部署 Kubernetes”升级为“理解调度、认证授权、网络、存储、多租户”的平台认知，减少把问题全甩给运维的盲区。
- 对工程化与 CI/CD：镜像构建、分发、数据卷、监控、配置中心、健康检查，是把项目从“能跑”变成“可持续交付”的关键治理面。
- 对你的技能树：这本书可作为 `docker-runtime -> container-platform -> kubernetes-control-plane` 的主干教材，后续再补 OCI、CNI、CSI、Helm、Operator、Service Mesh 时就有稳定骨架。
