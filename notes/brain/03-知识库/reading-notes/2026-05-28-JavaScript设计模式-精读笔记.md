## 章节地图 / Chapter map

### 第一部分：面向对象的 JavaScript

#### 第1章 富有表现力的 JavaScript

1. 这一章先把 JavaScript 定位成一门“足够灵活、足够动态”的语言：弱类型、函数一等公民、对象可变、继承机制不完全照搬类式语言。
2. 它的作用是给全书定调：设计模式不是把 Java/C++ 模式原样搬来，而是要在 JavaScript 自己的语言特性上重写。

#### 第2章 接口

3. 本章围绕“JavaScript 没有原生 interface，但大型协作仍需要接口约束”展开，先讲接口收益/代价，再讲如何用注释、属性检查、鸭式辨型来模拟接口。
4. `Interface` 类的引入意味着：哪怕语言层面缺位，工程层面也可以用约定、断言和运行时检查建立协作边界。

#### 第3章 封装和信息隐藏

5. 本章主线是“如何在开放的对象系统里保住边界”。它从门户大开型对象讲到命名规范、作用域、闭包、静态成员、常量、单体和对象工厂。
6. 对前端工程尤其关键的是：JavaScript 的封装不是默认给你的，而是需要你主动用闭包和模块边界换取可维护性。

#### 第4章 继承

7. 本章比较类式继承、原型式继承和掺元类，并给出“就地编辑”一类实际例子来观察三种方案在复用、覆盖、扩展上的差异。
8. 它不是为了鼓励到处继承，而是提醒读者：继承在 JavaScript 里成本不低，选错机制会让封装性和可理解性一起下降。

#### 第5章 单体模式

9. 本章把单体放在 JavaScript 页面环境里重讲：命名空间、网页专用包装器、私有成员、惰性实例化、分支技术，以及 XHR 对象创建示例。
10. 这里的单体不是 GoF 语境里的纯理论问题，而是浏览器时代前端代码如何避免全局污染、延迟初始化和做兼容分发的现实技巧。

#### 第6章 方法的链式调用

11. 第 6 章作为第一部分的收束点，说明“对象 API 不只是功能组合，还包含使用体验设计”：链式调用通过返回 `this` 或中间包装对象，把多步操作压缩成更流畅的调用链。
12. 在 JavaScript 语境里，这一章相当于把“可读性、可组合性、DSL 感”纳入模式讨论，为后面具体模式的 API 设计埋下伏笔。

### 第二部分：设计模式

#### 第7章 工厂模式

13. 工厂模式回答“对象该如何被创建而不泄露创建细节”。在 JavaScript 中，它特别适合屏蔽浏览器差异、数据源差异、组件构造差异。
14. 若把创建逻辑集中化，调用者就不再依赖具体构造细节，从而提高替换性与测试性。

#### 第8章 桥接模式

15. 桥接模式回答“抽象和实现如何解耦”。在前端里，它常用于把业务动作和底层实现分离，例如 UI 行为与事件绑定/网络层/平台适配分开演进。
16. 其价值是抑制组合爆炸：当两个维度都在变化时，不用为每一种组合写一个专门类。

#### 第9章 组合模式

17. 组合模式让单个对象与对象集合在使用上保持一致，适合描述树形结构、UI 容器、命令批处理等场景。
18. 对 JavaScript 而言，这一章通常连接到 DOM 树、组件树或任务树：调用方面对叶子和容器可以使用统一接口。

#### 第10章 门面模式

19. 门面模式把复杂子系统压缩成一个更简洁的入口。前端中常见为事件工具、动画工具、网络封装、跨浏览器兼容层。
20. 它不是“隐藏一切”，而是为 80% 常见路径提供低摩擦入口，同时保留底层系统的复杂度在门面之后。

#### 第11章 适配器模式

21. 适配器模式处理“已有接口不匹配，但又不值得重写”的问题，常见于旧接口升级、第三方库接入、后端响应结构不统一。
22. 它强调兼容性迁移：先适配、再替换，而不是把调用方一次性全部推倒重来。

#### 第12章 装饰者模式

23. 装饰者模式用组合而不是继承为对象附加职责，特别适合给 UI 组件、表单校验、日志、缓存、埋点增加横切能力。
24. 在 JavaScript 里，它往往比深继承树更自然，因为函数、闭包和对象包装让“增强”成本更低。

#### 第13章 享元模式

25. 享元模式的核心是共享可复用的内部状态，以降低大量细粒度对象带来的内存压力。
26. 浏览器场景下，它常与列表渲染、重复 DOM/样式、对象池思想关联，提醒读者区分共享状态与外部状态。

#### 第14章 代理模式

27. 代理模式把访问控制、延迟加载、缓存、远程调用、保护性封装放到真实对象之前。
28. 前端中可迁移到图片懒加载、请求代理、权限门禁、缓存代理等问题，重点是“控制访问而不改变调用方心智模型”。

#### 第15章 观察者模式

29. 观察者模式处理一对多通知，是事件系统、发布订阅、状态变化广播的基础。
30. 在 JavaScript 世界，这几乎是最有日常感的模式之一：DOM 事件、自定义 EventBus、响应式状态都可视为它的变体或近亲。

#### 第16章 命令模式

31. 命令模式把“请求”封装成对象，使得排队、撤销、重放、日志化、宏命令成为可能。
32. 对前端交互和工具系统来说，它适合表达按钮动作、编辑器操作、快捷键系统、批处理任务等可记录行为。

#### 第17章 职责链模式

33. 职责链模式把请求沿链路逐级传递，直到某个节点处理；适合表单校验链、鉴权链、事件冒泡式处理、兜底策略链。
34. 放在全书结尾很合理：它把前面多种“解耦”思想汇总成可扩展工作流的组织方式。

## 12 条关键概念 / examples

1. **设计模式在 JavaScript 里必须“按语言重写”。** 弱类型、函数一等公民、对象可变性决定了它不能机械照抄类式语言写法。
2. **接口缺位不等于接口思维缺位。** 即便没有 `interface` 关键字，团队仍需要契约、检查与鸭式辨型来守住协作边界。
3. **封装是主动争取来的，不是默认附赠的。** 命名规范、闭包、模块边界是 JavaScript 保持信息隐藏的主要手段。
4. **继承只是复用工具之一，不是首选信仰。** 原型链、clone、掺元类都各有成本，错误继承会放大耦合。
5. **单体模式在浏览器里首先是命名空间治理工具。** 它帮助你把页面级逻辑组织起来，避免全局变量污染。
6. **链式调用把 API 设计纳入模式讨论。** 返回 `this` 的设计不只是写法酷炫，而是为了更可读、更顺滑的组合体验。
7. **工厂模式把“创建变化”隔离开。** 当对象构造依赖环境、平台或策略时，工厂是天然落点。
8. **门面与适配器不要混淆。** 门面是给复杂系统提供更简单入口；适配器是让不兼容接口重新对齐。
9. **装饰者比深继承更适合横切增强。** 埋点、缓存、权限、校验等职责可以一层层附着，而不必污染核心对象。
10. **享元模式关心共享，代理模式关心控制。** 一个优化内存占用，一个控制访问路径，虽然都像“加一层”，目标不同。
11. **观察者、命令、职责链构成事件与流程组织三件套。** 一个解决通知，一个封装动作，一个组织处理路径。
12. **本书真正主题不是“背 11 个模式定义”，而是学习如何把常见前端问题改造成更模块化、更高效、更易维护的结构。**

## 学习主线 / 推荐二刷顺序

1. 第一遍先把第 1–6 章读成“JavaScript OOP 与 API 设计底座”，尤其关注接口模拟、闭包封装、原型/类式继承对比、单体与链式调用。
2. 第二遍按“创建型→结构型→行为型”重排后半部：工厂 → 桥接/组合/门面/适配器/装饰者/享元/代理 → 观察者/命令/职责链。
3. 第三遍把每个模式强制映射到自己做过的前端代码：组件、服务层、事件层、状态层、兼容层、性能层分别有哪些模式影子。
4. 第四遍输出一个“反模式对照表”：什么时候不该用单体、继承、观察者泛滥、过度门面或过度适配。

## 4 个实践练习

1. **练习 A：把一个松散脚本重构成命名空间单体**
   - 从现有前端项目找一段散落在页面里的脚本，重构为单体对象或模块对象。
   - 验收：全局泄漏变量减少；初始化入口清晰；私有成员与公开 API 分离。

2. **练习 B：为两个不兼容的数据源写适配器 + 门面**
   - 选择两个返回结构不同的接口，例如旧后端 DTO 与新 DTO，先写适配器对齐字段，再写门面暴露统一消费入口。
   - 验收：调用方无条件分支；替换底层实现时 UI 层改动最少。

3. **练习 C：用观察者 + 命令组织一个交互流程**
   - 例如表单提交流程：按钮点击触发命令对象，命令内部发起请求并通过观察者通知 loading、success、error。
   - 验收：动作可记录、可复放；界面更新与具体请求动作解耦。

4. **练习 D：给组件或 service 叠加装饰者**
   - 在不改核心逻辑前提下，为某个 service 增加日志、缓存、权限校验或重试能力。
   - 验收：增强逻辑可插拔；移除装饰层后核心对象仍正常工作。

## 对当前前端/后端/工程化能力的可落地应用点

**把本书沉淀为“前端架构中模式语汇”的统一字典。**

- 对前端 React/Vue 工程：可把 service 层、hooks、状态容器、UI 容器、事件总线、数据适配层分别映射到工厂、适配器、观察者、装饰者、门面等模式，减少“会写但讲不清”的隐性设计。
