## 全书主线 / What this book is really teaching

这本书的真正主线不是“背设计模式定义”，而是把 JavaScript 语言特性、前端日常场景与面向对象设计原则连成一个可操作体系：

1. 先理解 JavaScript 为什么不能机械照抄 Java/C++ 的模式写法。
2. 再把“变化封装、行为分发、接口协作、职责分离”映射到浏览器端真实问题。
3. 最后落到原则与重构，避免学成“模式名词收集器”。

用一句话概括：本书在教你把松散脚本、条件分支、全局污染和耦合逻辑，升级成可替换、可复用、可维护的前端结构。

## 章节地图 / Chapter map

### 第一部分：基础知识

#### 第1章 面向对象的 JavaScript
- 直接正文证据显示作者先解释动态类型、鸭子类型、多态、封装、原型模式和基于原型继承的对象系统。
- 这一章的重点不是复读 OOP 教科书，而是建立“JavaScript 的多态来自行为而非类型名”“原型委托是对象系统底座”的认知。
- 代表性例子包括：鸭子/鸡的 `makeSound`，地图渲染对象的 `show`，以及 `Object.create` / 原型链示例。

#### 第2章 this、call 和 apply
- 从目录可见，这一章聚焦 `this` 与 `call/apply` 两个核心主题。
- 它的作用是给后续模式实现提供函数调用上下文与显示绑定能力，否则很多模式代码只是“形似”而不真正可控。

#### 第3章 闭包和高阶函数
- 目录显示本章只分三块：闭包、高阶函数、小结，说明作者把它视为后续模式实现的函数式基础设施。
- 对 JavaScript 来说，这一章相当于告诉你：很多模式不一定要靠传统类层级，可以通过闭包与高阶函数更自然地表达。

### 第二部分：设计模式

#### 第4章 单例模式
- 目录表明本章覆盖透明单例、代理实现单例、JavaScript 中的单例、惰性单例与通用惰性单例。
- 可见作者关心的不是“全局只能有一个实例”的口号，而是页面级对象、登录框、缓存对象、命名空间和延迟初始化这类前端高频场景。

#### 第5章 策略模式
- 直接正文证据表明本章先用“年终奖计算”展示条件分支膨胀，再重构为策略对象/策略函数，把算法选择与算法实现分开。
- 同章目录继续延伸到缓动动画、表单校验、一等函数对象，说明作者强调策略模式在前端里不仅是算法题，更是 UI 行为、校验规则、动画曲线的组织方式。

#### 第6章 代理模式
- 目录给出了非常具体的 JavaScript 场景：图片预加载、合并 HTTP 请求、惰性加载、缓存代理、动态创建代理。
- 这说明代理模式在本书里被解释为“控制访问路径”的工程技巧，而不是抽象 UML 练习。

#### 第7章 迭代器模式
- 目录包含 `jQuery 中的迭代器`、内部/外部迭代器、类数组与字面量对象、倒序迭代器、中止迭代器。
- 这里的核心是把遍历逻辑从集合结构中抽离，让“怎么走”独立于“里面装了什么”。

#### 第8章 发布—订阅模式
- 目录显示作者从现实类比出发，落到 DOM 事件、自定义事件、通用实现、网站登录、全局事件对象、模块间通信、命名冲突。
- 对现代前端可直接迁移为 EventBus、跨模块通知、登录态广播、埋点与 UI 同步。

#### 第9章 命令模式
- 目录包含菜单程序、撤销命令、重做、命令队列、宏命令、智能命令与傻瓜命令。
- 说明本章重点是把“动作”变成可记录、可排队、可组合、可回滚的对象或函数。

#### 第10章 组合模式
- 目录包含宏命令、树中传递、扫描文件夹、父对象引用、何时使用组合模式。
- 这对应的是树形 UI、任务树、菜单树、文件树以及“容器/叶子统一对待”的设计需求。

#### 第11章 模板方法模式
- 目录出现 `Coffee or Tea`、抽象类、钩子方法、好莱坞原则、真的需要“继承”吗。
- 作者显然不仅讲模板方法经典写法，还主动讨论在 JavaScript 里是否一定要沿用继承式写法。

#### 第12章 享元模式
- 目录覆盖内部状态/外部状态、通用结构、文件上传例子、对象池。
- 这是在教你把“大量细粒度对象”的问题重写成共享与外部化状态的问题，适合性能与资源治理。

#### 第13章 职责链模式
- 目录包含现实案例、重构代码、灵活可拆分节点、异步职责链、AOP 实现职责链、获取文件上传对象。
- 这意味着作者把职责链落到了前端常见的校验链、容错链、上传能力降级链与异步流水线上。

#### 第14章 中介者模式
- 目录用“泡泡堂游戏”和“购买商品”做例子。
- 典型问题是多对象网状耦合，用中介者把对象之间的显式互相引用收束到中心调度点。

#### 第15章 装饰者模式
- 目录包括回到 JavaScript 的装饰者、装饰函数、AOP 装饰函数、AOP 应用实例，以及装饰者模式和代理模式对比。
- 这直接连接到 today frontend 的日志、鉴权、缓存、埋点、节流、防抖、重试等横切增强。

#### 第16章 状态模式
- 目录覆盖文件上传示例、性能优化点、策略模式关系、JavaScript 版本状态机、表驱动有限状态机。
- 说明作者把状态模式解释成“显式状态转移 + 行为切换”的统一框架，而不仅是 if-else 美化。

#### 第17章 适配器模式
- 目录虽短，但非常精准：现实中的适配器、适配器模式的应用、小结。
- 这章像一把工程小刀，专门解决旧接口、新接口、第三方接口与调用方预期不一致的问题。

### 第三部分：设计原则和编程技巧

#### 第18章 单一职责原则
- 目录强调何时分离职责、违反 SRP 的后果与 SRP 优缺点。
- 它是全书前半段模式练习背后的总规则：别让一个对象同时承担过多变化原因。

#### 第19章 最少知识原则
- 目录关键词是“减少对象之间的联系”“封装在 LKP 中的体现”。
- 核心意思是少知道、少依赖、少穿透，避免对象之间形成脆弱耦合网络。

#### 第20章 开放—封闭原则
- 目录出现 `扩展 window.onload`、`用对象的多态性消除条件分支`、`找出变化的地方`、`接受第一次愚弄`。
- 这说明作者不是抽象说教，而是把 OCP 落到非常具体的前端脚本扩展与重构策略上。

#### 第21章 接口和面向接口编程
- 目录显示作者从 Java 抽象类/interface 讲回 JavaScript，最后落到“用鸭子类型进行接口检查”与“用 TypeScript 编写基于 interface 的命令模式”。
- 这一章的价值在于把静态语言的接口思想翻译成 JavaScript/TypeScript 可执行实践。

#### 第22章 代码重构
- 目录给出一串极实用的动作：提炼函数、合并重复条件片段、提炼条件分支、减少参数、少用三目、合理使用链式调用、分解大型类、`return` 退出多重循环。
- 这章相当于把全书从“设计模式理念”收束到“日常改代码的手”。

## 15 条关键概念 / examples

1. 设计模式在 JavaScript 中必须按语言特性重写，不能照搬类式语言模板。
2. 鸭子类型强调关注行为能力而不是名义类型；“会不会做”比“是什么类”更重要。
3. 多态的真正收益不是炫技，而是消除按类型分支的条件语句。
4. `renderMap(map)` 这种接口，比 `renderMap('google')` 这种按类型分支的接口更可扩展。
5. 封装不只是藏数据，还包括隐藏实现、隐藏类型、隐藏变化。
6. 原型模式在 JavaScript 里不是边缘知识，而是对象系统本体。
7. 闭包和高阶函数让很多模式可以不借助繁重类层级就落地。
8. 单例模式在前端首先是命名空间和延迟初始化治理问题。
9. 策略模式的本质是把“算法选择”与“算法实现”拆开，让奖金计算、缓动动画、表单校验都能替换。
10. 代理模式关心控制访问：预加载、合并请求、缓存、懒加载都是其自然场景。
11. 发布—订阅、命令、职责链、状态机共同构成前端交互流程的四大组织方式。
12. 装饰者模式比深继承更适合加日志、埋点、权限、缓存等横切能力。
13. 享元模式和对象池体现了作者对前端性能与资源复用的重视，而不只是书斋式模式分类。
14. 开放—封闭原则在本书里被具体化为“找出变化并封装”“尽量用扩展代替修改”。
15. 最终落点不是模式背诵，而是把脚本、组件、服务层、事件流和重构动作组织成长期可维护代码。

## 学习顺序建议 / Recommended reread path

1. 先通读第 1–3 章，把“鸭子类型、多态、闭包、高阶函数、原型系统”读成 JavaScript 设计模式语法底座。
2. 第二轮优先读第 5、6、8、9、13、15、16、17 章，因为这些最贴近日常前端工程：校验、请求、事件、命令、流程、增强、状态与接口兼容。
3. 第三轮回到第 18–22 章，把模式用原则和重构语言重新解释一遍，形成“何时该用/何时不该用”的判断力。
4. 第四轮把书中每章都映射到自己的真实代码：hooks/service/BFF adapter/state machine/event bus/upload pipeline/component wrapper。

## 6 个实践任务 / Practice tasks

1. 练习 A：把绩效奖金例子改写成 TypeScript 版策略模式
   - 要求：分别实现函数式策略版、对象策略版。
   - 验收：新增策略不改上下文主流程，只新增策略实现。

2. 练习 B：把现有表单校验链重构为“策略 + 职责链”
   - 要求：同步校验与异步校验都能组合。
   - 验收：字段规则新增时不改原主链控制流。

3. 练习 C：为图片/数据请求实现“虚拟代理 + 缓存代理”
   - 要求：首屏懒加载、重复请求合并、热点结果缓存。
   - 验收：调用方只面向统一接口，不关心预加载/缓存细节。

4. 练习 D：把事件散落页面改成发布—订阅总线
   - 要求：登录成功、购物车变化、主题切换等事件统一通过总线广播。
   - 验收：新增订阅者不改发布者实现。

5. 练习 E：把上传流程改成显式状态机
   - 要求：待上传/上传中/暂停/成功/失败/重试状态明确，禁止隐式布尔拼接。
   - 验收：状态转移表可读，非法转移有守卫。

6. 练习 F：做一次“第 22 章风格”的实战重构
   - 要求：从现有项目找一个 150+ 行函数，按提炼函数、消减参数、提前返回、分解大型类改造。
   - 验收：行为不变，测试通过，复杂条件明显减少。

## 对当前前端/全栈工程的迁移价值

1. React/Vue 组件层：装饰者可映射 HOC / hooks wrapper / middleware；组合模式可映射容器-叶子组件树。
2. Service/BFF 层：适配器模式可承接旧 DTO、新 DTO、第三方接口响应差异。
3. 状态管理层：发布—订阅 + 状态模式能解释 store、event bus、workflow machine 的设计边界。
4. 上传/下载/轮询/表单流程：职责链、命令、状态模式可以把“散 if-else”重构为明确流程节点。
5. 性能治理层：享元、对象池、缓存代理可以映射到列表渲染、资源池、请求去重与 memoization。
6. 架构评审语言：第 18–22 章提供了比“代码优雅/不优雅”更硬的评审话术，可直接用于 code review 与设计审查。
