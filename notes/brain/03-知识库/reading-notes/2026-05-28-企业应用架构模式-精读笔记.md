## 章节地图 / Chapter map

### 引言：为什么企业应用需要独立的架构模式语汇

1. 书在开场先回答“企业应用和普通桌面/算法程序有什么不同”：它们更强调长期演化、关系数据库、事务、一致性、并发、多层边界、分布式协作与复杂业务规则。
2. `0.1 ~ 0.5` 这一组小节的作用，是建立阅读框架：架构不是“大图”，而是围绕边界、职责、性能代价与变化点做约束设计。

### 第一部分：表述 / Narratives

#### 第1章 分层

3. 第 1 章用企业应用分层演化说明：表现、领域、数据源至少要逻辑分离，否则 UI、业务规则和数据库细节会缠死在一起。
4. “三个基本层次 + 为各层选择运行环境”意味着作者关心的不是教条式三层，而是“变化率不同的责任要不要放在同一个地方”。

#### 第2章 组织领域逻辑

5. 这一章是全书最关键的决策入口：业务规则究竟放在事务脚本、领域模型、表模块还是服务层中。
6. 它实际上在回答一个长期问题：系统复杂度上升时，代码应该围绕“用例流程”“对象模型”还是“数据表”来组织。

#### 第3章 映射到关系数据库

7. 第 3 章把对象世界与关系世界之间的张力单独拉出来：既包括架构模式，也包括读取数据、结构映射、元数据、连接管理等工程问题。
8. 这一章说明 ORM 不是“框架功能”，而是系统复杂度真正的来源之一，因为对象边界和表结构边界天然不一致。

#### 第4章 Web 表现层

9. 这里把视图模式和输入控制器模式拆开讲，说明 Web 层不只是模板渲染，它还承担请求解释、导航控制、用户流程组织与表现逻辑装配。
10. 对今天的前端/后端协作而言，这一章仍然重要，因为它定义了控制器、页面、视图转换之间的职责边界。

#### 第5章 并发

11. 第 5 章从并发问题、执行语境、隔离与不变性切入，再讨论乐观/悲观并发控制与事务。
12. 它把“正确性”放在“吞吐”之前：企业应用的核心不是更快，而是多人/多事务同时操作时不把业务状态写坏。

#### 第6章 会话状态

13. 作者先讲无状态的价值，再讲会话状态及其存储方式，说明会话不是白拿的便利，而是一种要付出扩展性与一致性成本的设计选择。
14. 这一章直接影响今天的 BFF、SSR、API Gateway、登录态、购物车、草稿箱等系统设计。

#### 第7章 分布策略

15. 书里并不盲目推崇分布式，而是先讨论“分布对象的诱惑”和远程/本地接口差异。
16. 重点是提醒读者：只要跨进程、跨机器，调用语义、性能模型、失败模式就已经和本地对象完全不同。

#### 第8章 通盘考虑

17. 这一章相当于前面叙事部分的收束：从领域层开始，再深入数据源层、表现层，并给出若干具体技术建议。
18. 它强调架构不是孤立套模式，而是从业务模型往外推导：领域逻辑先稳，再决定持久化和 UI 的承载方式。

### 第二部分：模式 / Catalog

#### 第9章 领域逻辑模式

19. 事务脚本、领域模型、表模块、服务层四种模式构成业务逻辑组织的主轴；这四者几乎决定了系统后续可维护性上限。
20. 可以把它理解为“你准备把复杂度放在哪里”的四种不同答案。

#### 第10章 数据源架构模式

21. 表数据入口、行数据入口、活动记录、数据映射器构成从“贴表写逻辑”到“领域对象与持久化彻底解耦”的一条连续谱。
22. 这章最适合拿来审视当前项目是否陷入了 Repository/Mapper/Entity 职责混杂。

#### 第11章 对象-关系行为模式

23. 工作单元、标识映射、延迟加载三者共同解决“一个业务操作里对象怎么保持一致、去重和按需取数”。
24. 这是多数 ORM 真正难调试的地方：不是 CRUD，而是对象身份、事务边界和加载时机。

#### 第12章 对象-关系结构模式

25. 从标识域、外键映射、关联表映射，到单表继承、类表继承、具体表继承，这一章系统梳理对象结构如何落到表结构。
26. 它告诉我们：继承、组合、关联一旦进入数据库，就不再只是面向对象设计题，而是查询成本、约束表达和演化成本的综合题。

#### 第13章 对象-关系元数据映射模式

27. 元数据映射、查询对象、资源库让映射关系与查询语义进一步从业务代码中抽离出来。
28. 这章的价值在于把“查询”提升为独立设计对象，而不是散落在服务层里的 SQL 字符串。

#### 第14章 Web 表现模式

29. MVC、页面控制器、前端控制器、模板视图、转换视图、两步视图、应用控制器，构成 Web 请求到 HTML/页面响应的完整模式族。
30. 今天看，它们仍然对应前后端路由、控制器层、服务端模板、前端渲染管线、页面编排与跨页面导航规则。

#### 第15章 分布模式

31. 远程外观和数据传输对象是分布式边界上的两个关键模式：前者通过粗粒度接口减少远程聊天式调用，后者通过专用数据包降低网络语义摩擦。
32. 这组模式对今天的 BFF、GraphQL 聚合层、RPC DTO、后端接口编排仍然完全适用。

#### 第16章 离线并发模式

33. 乐观离线锁、悲观离线锁、粗粒度锁、隐含锁回答的是“用户与事务不在同一瞬时上下文里时，如何保护数据正确性”。
34. 它直接映射到表单编辑、审批流、库存扣减、长事务后台管理系统等现代场景。

#### 第17章 会话状态模式

35. 客户会话状态、服务器会话状态、数据库会话状态是对状态存放位置的三种明确选择。
36. 作者想表达的是：状态永远要放 somewhere，但放在哪儿会改变扩展性、可靠性与运维代价。

#### 第18章 基本模式

37. 入口、映射器、层超类型、分离接口、注册表、值对象、货币、特殊情况、插件、服务桩、记录集，像是一组可复用“基础积木”。
38. 这些模式的重要性在于：很多企业系统不是缺“大架构”，而是缺这批稳定的低层表达工具，导致重复样板和边界污染。

## 12 条关键概念 / examples

1. **企业应用的难点不在算法，而在边界与一致性。** 这类系统要长期承载业务演化，所以“层次、事务、并发、会话、分布”比炫技实现更重要。
2. **分层的目标不是形式统一，而是变化隔离。** 表现层、领域层、数据源层拆开，是为了让 UI 变化、规则变化、存储变化不要彼此拖死。
3. **领域逻辑的组织方式决定系统寿命。** 事务脚本适合简单流程；领域模型适合复杂规则；表模块偏报表/数据驱动；服务层则用于把用例边界讲清楚。
4. **对象关系映射是企业应用的第一复杂度放大器。** 一旦对象模型与数据库模型不一致，身份、一致性、关联、继承、查询都需要额外设计。
5. **Repository / Query Object / Metadata Mapping 的价值在于把查询与映射从业务代码里抽离。** 否则服务层会很快退化为 SQL 拼装层。
6. **Web 表现层本身也有模式，不只是“Controller 接 Request”。** MVC、Page Controller、Front Controller、Application Controller分别对应不同粒度的请求组织方式。
7. **远程调用不是本地调用的延长线。** 远程外观与 DTO 提醒我们：跨网络之后，粗粒度接口、批量数据、失败隔离都比对象纯度更重要。
8. **事务与并发策略必须贴着业务不变量设计。** 乐观锁/悲观锁没有抽象优劣，关键看冲突频率、补偿成本和用户交互时长。
9. **会话状态的放置位置是一种架构选择。** 放客户端、服务器、数据库，各自交换的是性能、可扩展性、同步复杂度与故障恢复方式。
10. **很多“框架最佳实践”其实都是本书模式的现代包装。** 例如 Service、Repository、DTO、Unit of Work、Identity Map、Lazy Load、Front Controller 今天仍然高频出现。
11. **模式不是模板，而是命名过的问题-解法对。** 真正价值是帮助团队在讨论架构时快速达成上下文，而不是机械套用类图。
12. **企业应用架构的核心方法论是先识别主复杂度，再决定模式组合。** 不是所有系统都值得上完整 DDD + ORM + 分布式，而是要按业务复杂度和演化预期选型。

## 学习主线 / 推荐二刷顺序

1. 第一遍读“叙事主线”：引言 + 第 1~8 章，先搞清企业应用为什么会出现这些经典难题。
2. 第二遍读“业务逻辑主线”：第 9 章 + 第 10~13 章，把领域逻辑组织和 ORM 相关模式串起来。
3. 第三遍读“Web 与分布主线”：第 14~17 章，把请求控制、远程边界、会话状态和离线并发放到一个系统里看。
4. 第四遍读“基础积木主线”：第 18 章，把 Gateway、Mapper、Registry、Value Object、Plugin、Service Stub 等低层表达方式补齐。

## 4 个实践练习

1. **练习 A：给当前项目画一张“模式落点图”**
   - 任选一个中大型项目模块，标出它当前更像 Transaction Script、Domain Model、Table Module 还是混合形态。
   - 验收：能给出 3 处“职责混杂点”和 1 个最值得先重构的边界。

2. **练习 B：做一次 ORM 反向体检**
   - 列出项目中的 Entity / DTO / Repository / Mapper / Service。
   - 检查是否出现 Active Record、Data Mapper、Repository、Unit of Work 混用且职责不清。
   - 验收：至少指出 2 个“查询逻辑泄漏到服务层”或“持久化语义污染领域层”的例子。

3. **练习 C：重写一个远程接口为粗粒度接口**
   - 找一个前端页面需要连续调用多个接口拼装数据的场景。
   - 设计一个更接近 Remote Facade + DTO 的聚合接口，减少聊天式往返。
   - 验收：说明减少了哪些 round-trip、牺牲了哪些灵活性、如何控制接口膨胀。

4. **练习 D：为一个长事务页面设计并发保护**
   - 选一个“用户打开页面编辑 5 分钟后再提交”的后台表单或审批场景。
   - 分别设计 Optimistic Offline Lock 与 Pessimistic Offline Lock 两个方案。
   - 验收：比较冲突提示、用户体验、实现难度与回滚策略，并说明为什么最终选其中一种。

## 对现代工程的可落地应用点

**把《企业应用架构模式》当成“把混乱业务系统重新命名、分层和去耦”的诊断手册。**

- 对后端架构：它最适合拿来识别“到底该上领域模型，还是继续事务脚本”的分水岭，避免在不必要的地方过度设计，也避免在复杂规则场景继续堆 if/else。
- 对全栈/前端：第 14~17 章能直接帮助理解 BFF、页面编排、表单长事务、会话状态和接口聚合，减少“前端只是调接口”的窄视角。
- 对遗留系统治理：第 10~13 章提供了一套拆 ORM 混乱、理清 Entity/DTO/Mapper/Repository 职责的术语表，非常适合作为架构评审 checklist。
- 对分布式系统设计：Remote Facade + DTO + Offline Lock 的组合，今天仍然是设计聚合接口、异步审批、库存一致性和管理后台编辑冲突的高频工具。
