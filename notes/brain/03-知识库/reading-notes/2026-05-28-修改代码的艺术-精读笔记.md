## 章节地图 / Chapter map

### 第一部分：修改机理（第 1–5 章）

1. `第1章 修改软件`：从“添加新特性 / 修正 bug / 改善设计 / 优化资源使用”四种修改动机切入，解释为什么代码修改本身不是问题，问题在于缺乏方法论的修改。
2. `第2章 带着反馈工作`：用 “edit and pray（编辑并祈祷）” 对照 “cover and modify（覆盖并修改）”，把测试定义为修改时的安全网与反馈回路。
3. `第3章 感知和分离`：说明解依赖的两个核心目标——感知（sensing）与分离（separation），并引入伪对象/仿对象来观察副作用。
4. `第4章 接缝模型`：提出 seam 视角，把既有代码看成可切入、可替换的接缝网络，而不是一整坨不可碰的文本。
5. `第5章 工具`：梳理编辑器/IDE、构建系统、测试框架、自动化重构工具在遗留代码治理中的角色边界。

### 第二部分：修改代码的技术（第 6–24 章）

6. `第6章 时间紧迫，但必须修改`：回答“先写测试/先解依赖会不会拖慢交付”——短期会多做工作，但通常能减少反复返工和调试时间。
7. `第7章 漫长的修改`：讨论长周期修改里的理解、时滞与解依赖策略，强调持续反馈。
8. `第8章 添加特性`：把 TDD 作为添加特性的最强路径，同时警惕“新生方法/类、外覆方法/类”只止血不治本。
9. `第9章 无法将类放入测试用具中`：处理构造参数、隐藏依赖、全局依赖、包含依赖等对象级阻塞。
10. `第10章 无法在测试用具中运行方法`：处理方法级阻塞，如隐藏方法、不可探知副作用等。
11. `第11章 修改时应当测试哪些方法`：做影响分析，决定在哪里布测试最划算。
12. `第12章 在同一地进行多处修改，是否应该将相关的所有类都解依赖`：通过拦截点/汇点决定范围与策略。
13. `第13章 修改时应该怎样写测试`：引入特征测试（characterization / feature tests），先把现有行为固定住再改。
14. `第14章 棘手的库依赖问题`：处理外部库绑定导致的测试困难。
15. `第15章 到处都是 API 调用`：治理系统边界污染、隔离外部调用。
16. `第16章 对代码的理解不足`：用注记、草图、草稿式重构、删死代码等方式加速理解。
17. `第17章 应用毫无结构可言`：当系统已经“hack point 驱动”时，如何重建全局故事与共享架构理解。
18. `第18章 测试代码碍手碍脚`：通过命名、目录、测试子类/Fake 组织，降低测试代码认知成本。
19. `第19章 对非面向对象的项目，如何安全地对它进行修改`：面向 C/COBOL/FORTRAN 等过程式遗留系统的安全修改策略。
20. `第20章 处理大类`：识别职责膨胀，优先用新生类/新生方法防止继续恶化。
21. `第21章 需要修改大量相同的代码`：用小步重构处理重复，而不是忍着复制粘贴债务继续增长。
22. `第22章 要修改一个巨型方法，却没法为它编写测试`：把巨型方法视作沼泽，靠分块、提取、理解局部逐步推进。
23. `第23章 降低修改的风险`：讲机械层与心理层的风险控制，如把行为改变与纯重构分开。
24. `第24章 当你感到绝望时`：处理遗留系统工作中的心态与组织困境，提醒“重写一切”并不天然更优。

## 15 条关键概念 / examples

1. **遗留代码的关键定义不是“别人写的老代码”，而是“没有测试的代码”。** 前言明确给出这个重定义：无测试，就无法快速验证修改后的行为是否变好还是变坏。
2. **软件修改只有四大动机：加特性、修 bug、改善设计、优化资源。** 这是建立问题分类和决策路径的起点。
3. **“编辑并祈祷”是业界默认坏习惯。** 第 2 章把它描述为：先改，再跑系统，再祈祷没炸。
4. **“覆盖并修改”要求先张开测试安全网。** 测试不是事后审判，而是修改时的实时反馈系统。
5. **自动化测试的首要价值不只是找 bug，而是检测变化。** 手动测试可以发现问题，但自动化测试更适合守住既有行为边界。
6. **解依赖的两个原因只有两个：感知与分离。** 看不到结果，就无法感知；放不进测试，就必须分离。
7. **接缝（seam）是遗留代码可治理性的核心抽象。** 你不是直接“重写整坨代码”，而是在能替换/能绕开的边界上切入。
8. **时间紧时先解依赖/先补测试，通常是延迟满足而不是纯成本。** 第 6 章强调：早做两小时，常能省后面更长时间的调试和返工。
9. **添加特性时，TDD 是最强技术；新生方法/类、外覆方法/类只是权宜之计。** 它们能绕开风险，但可能把设计债往后推。
10. **测试点选择要靠影响分析，而不是“见方法就测”。** 第 11 章强调要推断改动如何传播到其他行为边界。
11. **特征测试的作用是先固定现有行为，再安全修改。** 它不要求你先知道理想行为，只要求你先抓住当前行为。
12. **理解陌生代码时，草图和注记不是低效动作，而是降低后续误判的前置投资。** 第 16 章明确反对“只靠脑内推演”。
13. **系统架构不能只存在于架构师脑中。** 第 17 章指出，团队若没有共享结构理解，系统会退化成围绕 hack point 工作。
14. **测试代码也需要架构。** 命名规范、Fake 目录、Testing 子类前缀等做法，是降低维护摩擦的组织策略。
15. **解依赖技术本身不是最终设计目标，而是把代码送入测试保护区的过桥工具。** 第 25 章明确提醒：先求可验证，再谈更大规模重构。

## 学习主线 / 推荐二刷顺序

1. 第一遍读 `前言 + 第1–4章`：建立“遗留代码 = 无测试代码”“感知/分离”“接缝”三大世界观。
2. 第二遍读 `第6/8/11/13/23/25章`：把“先写哪些测试、如何安全修改、如何解依赖”串成可执行算法。
3. 第三遍按自己常见痛点选读 `第16–22章`：理解不足、结构混乱、大类、重复代码、巨型方法，这些都是项目日常高频场景。
4. 最后回头看 `第17/24章`：把遗留代码治理从个人技术问题，提升为团队协作与组织韧性问题。

## 5 个实践练习

1. **练习 A：给一个真实遗留模块做“修改动机四分法”标注**
   - 从你当前项目里选 10 个待改项，分别标记是“加特性 / 修 bug / 改善设计 / 优化资源”。
   - 验收：每个待改项都写明为什么属于该类，避免把所有事情都笼统叫“优化”。

2. **练习 B：把一个高风险改动改写成“覆盖并修改”流程**
   - 选一个你本来会直接改的函数，先补 1–3 个特征测试，再做改动。
   - 验收：明确记录“如果不先补测试，我原本会如何编辑并祈祷”。

3. **练习 C：为一个难测类画感知/分离草图**
   - 列出它的依赖、哪些输出目前无法感知、哪些依赖阻止它被放进测试。
   - 验收：给出至少 1 个 seam 或 fake/接口提取候选点。

4. **练习 D：对一个巨型方法做局部降解**
   - 不要求一次重构完；只把其中一个你真正理解的片段提取成新方法或方法对象。
   - 验收：提取后新增测试仍能说明行为未变。

5. **练习 E：建立测试代码组织约定**
   - 给项目统一 `FooTest` / `FakeBar` / `TestingBaz` 命名、目录位置和最小注释规范。
   - 验收：新成员仅凭类名能快速区分产品代码、测试类、Fake、测试子类。

## 对当前前端/后端/工程化能力的可落地应用点

**把《修改代码的艺术》沉淀成“遗留改动前置检查单 + 解依赖 playbook”，用于全栈项目与 Hermes 自身演化。**

- 对前端：把复杂 React/Vue 页面改动先转成“特征测试 + seam 识别”问题，避免直接在耦合组件里编辑并祈祷。
- 对后端：在 Controller/Service/DAO 或外部 API 调用密集区，优先识别可加 Fake/接口提取/委托的位置，再推动安全重构。
- 对工程化：把“行为改变”和“纯重构”拆开提交；先建立测试安全网，再做结构优化，减少 review 噪声和回滚风险。
- 对过程式/脚本型基础设施：善用连接期接缝、参数适配、封装全局引用，降低 shell/python 脚本型遗留逻辑的改动风险。
- 对 Hermes / 工作流：可沉淀一个 `legacy-code-change-playbook` 视角，要求任何复杂修改先回答四个问题：改动动机是什么、测试点在哪、接缝在哪、如何避免编辑并祈祷。
