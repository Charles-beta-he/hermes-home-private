## 章节地图 / Chapter map

### Part 1：简单数据的处理（第1–8章）

1. `第1章 学生、教师和计算机`：先建立“程序设计是一种可教、可练、可分解的方法”这一学习契约。
2. `第2章 数、表达式和简单程序`：从数、算术运算、变量、字处理切入，说明程序最初是对简单数据施加变换。
3. `第3章 程序就是函数加上变量定义`：把函数复合和变量定义绑定起来，形成最早的设计配方。
4. `第4章 条件表达式和函数`：加入布尔关系与条件分支，建立“输入分类 → 条件判断 → 对应函数”的模式。
5. `第5章 符号信息`：把计算从纯数字扩展到符号与标签，提示“数据种类”决定程序形态。
6. `第6章 复合数据之一：结构体`：引入结构体、数据定义和处理复合数据的函数，开始把“程序设计”升级为“围绕数据定义写模板”。
7. `第7章 数据的多样性`：处理 mixed data / union data，强调先区分变体，再为每种变体设计分支。
8. `第8章 语法和语义`：回头解释语言表达式、变量定义与结构体定义的语法/语义，给方法论补语言学底座。

### Part 2：任意数目数据的处理（第9–13章）

9. `第9章 复合数据类型之二：表`：从固定形状结构体迈向任意长度表，进入递归数据定义。
10. `第10章 表的进一步处理`：处理返回表的函数、包含结构体的表，说明“数据容器里再嵌套数据”。
11. `第11章 自然数`：用自然数本身做数据定义对象，训练读者把数学对象也看成可递归分解的数据。
12. `第12章 三论函数复合`：把复杂程序拆成辅助函数、问题泛化和函数泛化，强化设计步骤复用。
13. `第13章 用list构造表`：把前述表处理方法落到 `list` 这种语言内建抽象上。

### Part 3：再论任意大数据的处理（第14–18章）

14. `第14章 再论自引用数据定义`：从简单递归表转向结构体中的结构体、树等更复杂递归对象。
15. `第15章 相互引用的数据定义`：处理 mutually recursive data，逼迫读者把模板设计推进到多类型协作。
16. `第16章 反复精化设计`：数据分析 → 数据定义改进 → 函数改进，体现迭代式设计方法。
17. `第17章 处理两种复杂数据片段`：同时读入和处理两个复杂输入，训练多输入递归模板。
18. `第18章 局部定义和辖域`：用 `local`、块结构和作用域组织复杂程序，降低全局复杂度。

### Part 4：抽象设计（第19–24章）

19. `第19章 定义的相似性`：先发现函数之间、数据定义之间的相似模式。
20. `第20章 函数也是值`：把函数提升为一等值，引出多态函数与抽象函数合约。
21. `第21章 抽象设计的例子`：从实例中抽出模板，再把模板固化为“唯一控制点”。
22. `第22章 使用函数进行抽象设计`：进入高阶函数、返回函数的函数，以及 GUI 初探。
23. `第23章 数学方面的例子`：把抽象设计迁移到数列、级数、面积、斜率等数学问题。
24. `第24章 定义匿名函数`：`lambda` 的语法、作用域、语义与用法，补足抽象表达能力。

### Part 5：生成递归（第25–29章）

25. `第25章 一种新的递归形式`：从结构递归转入生成递归，讨论“递归如何创造新的子问题”。
26. `第26章 设计算法`：围绕终止性与结构递归/生成递归的比较来选算法路线。
27. `第27章 主题的变更`：把生成递归应用到分形、文件处理、二分查找、牛顿法、高斯消去。
28. `第28章 回溯算法`：图遍历、八皇后等问题把搜索树带入设计方法。
29. `第29章 计算的代价和向量`：开始引入复杂度与向量抽象，为后面的状态与可变数据铺垫。

### Part 6：知识累积（第30–33章）

30. `第30章 知识的丢失`：讨论为什么某些结构递归或生成递归会丢失过程中间知识。
31. `第31章 设计带累积器的函数`：累积器作为保存中间知识的系统手段登场。
32. `第32章 使用累积器的更多例子`：把累积器迁移到树、传教士和食人者、单人跳棋等复杂搜索场景。
33. `第33章 非精确数的本质`：讨论固定长度数、上溢/下溢、DrScheme 数值，提醒程序设计受到底层表示约束。

### Part 7：改变变量的状态（第34–38章）

34. `第34章 函数的记忆`：开始从纯函数世界迈向带状态程序。
35. `第35章 对变量赋值`：讨论赋值、顺序计算表达式以及赋值对函数语义的影响。
36. `第36章 设计有记忆的函数`：围绕状态变量、初始化和状态变更设计真正有记忆的函数。
37. `第37章 使用记忆的例子`：交互、递归中改变状态、探险练习，把状态带入实际程序。
38. `第38章 最终的语法和语义`：给引入状态后的语言一个更完整的语法语义收束。

### Part 8：复合值的改变（第39–43章）

39. `第39章 封装`：把状态变量抽象起来，说明为什么“方法”最终会走到封装。
40. `第40章 可改变的结构体`：结构体、向量等复合值变为可变对象。

43. `第43章 修改结构体、向量和对象`：以循环结构、回溯状态等问题作为全书方法收束。

## 12 条关键概念 / examples

1. **本书真正核心是“从数据定义出发设计程序”。** 先问数据长什么样，再问函数模板长什么样，而不是先写流程后补结构。
2. **简单数据 → 复合数据 → 任意长数据 → 相互引用数据，是一条能力阶梯。** 每跨一级，函数设计模板都要升级。
3. **条件分支来自数据分类，而不是来自随意的 if/else 堆叠。** 先分类输入，再为每类写规则，是降低分支混乱的关键。
4. **结构体不是语法点，而是建模边界。** 一旦数据被封成结构体，字段、构造器、访问器和处理模板就都固定下来。
5. **表与树让递归成为“数据驱动的必然”，不是技巧。** 递归之所以成立，是因为数据定义本身自引用。
6. **局部定义与辖域是复杂度治理工具。** `local`/块结构不是装饰，而是避免辅助函数污染全局命名空间的工程手段。
7. **抽象不是越早越好，而是在看见相似性之后提炼唯一控制点。** 第19–22章把“重复”升级为“有证据的抽象”。
8. **高阶函数把“程序步骤”本身变成数据。** 当函数也是值，模式复用就不再停留在复制粘贴。
9. **生成递归与结构递归是两种不同的算法思维。** 前者强调制造新子问题，后者强调沿已有数据结构拆解。
10. **累积器是防止知识丢失的结构化补丁。** 它把“中间状态”显式化，而不是让递归隐式吞掉信息。
11. **状态与赋值改变的不只是代码写法，还改变程序语义模型。** 一旦进入第34章以后，测试、相等、封装、回溯都要重新理解。
12. **向量/可变结构体提醒我们：数据结构选择直接影响复杂度与设计方式。** 豆瓣公开摘录中 `vector-ref` 的 `O(1)` 就是这一点的直接证据。

## 学习主线 / 推荐二刷顺序

1. 第一遍先把 Part 1–3 读成“数据定义驱动设计”的核心路线：简单数据 → 结构体 → mixed data → 表 → 树 → 相互引用数据。
2. 第二遍重点读 Part 4–6，把抽象设计、高阶函数、生成递归、累积器看成“从会写程序到会设计程序”的跃迁。
3. 第三遍再读 Part 7–8，把状态、赋值、封装、可变结构体和相等连成一个“命令式副作用治理包”。
4. 每读完一个部分，都回到自己的真实代码库里找一个对应场景：表单状态、树形菜单、AST、路由配置、递归渲染、缓存/状态管理、可变 store 等，强制做映射。

## 4 个实践练习

1. **练习 A：把一个前端复杂表单重写成“数据定义 + 模板函数”**
   - 选一个多步骤表单，把字段分成简单字段、结构体字段、联合字段（例如不同签证类型）。
   - 验收：类型定义先行；每个分支都有稳定渲染/校验模板；业务分支不是散落在组件里的条件拼接。

2. **练习 B：为树形/递归 UI 写结构递归模板**
   - 选菜单树、评论树、组织树或路由树，先写数据定义，再写递归遍历、查找、映射三个函数。
   - 验收：所有递归都能从数据定义直接推导；新增节点类型时能定位到唯一模板改动点。

3. **练习 C：用高阶函数抽掉重复列表逻辑**
   - 从 React/Vue 项目里找三段相似的 `map/filter/reduce` 或校验逻辑，提炼为高阶函数或 hook。
   - 验收：重复逻辑减少；调用方只传策略函数；唯一控制点清晰。

4. **练习 D：给一个带缓存/撤销需求的模块设计累积器或状态变量**
   - 可选搜索历史、草稿保存、步骤回退、任务回放等场景，先写纯函数版本，再写带累积器/状态版本比较。
   - 验收：能解释为什么必须引入状态；能说明相等、测试和回溯策略如何变化。

## 对当前前端/后端/工程化能力的可落地应用点

**把 HtDP 的“数据定义驱动设计”迁移成 TypeScript/全栈项目里的建模优先工作流。**

- 对前端 React/Vue：把组件状态、表单 schema、树形数据、异步状态机先建模为 discriminated unions / interfaces，再从类型反推渲染、校验和事件处理模板。
- 对后端/BFF：把 DTO、聚合对象、分页表、树形响应、递归目录结构先写成清晰的数据定义，再决定 handler/service 的函数模板，减少“接口一变，分支到处炸”。
- 对工程化：把抽象设计与唯一控制点迁移到 hooks、工具函数、代码生成模板、表驱动配置和 lintable contract 上。
- 对 Hermes / 技能树：可以沉淀一个 `data-definition-driven-review` 审查视角，用来检查代码是否“先有数据模型与变体边界，再有流程逻辑”，从而抑制散乱条件分支与无模板递归。
