## 章节地图 / Chapter map

### 第1章 Introduction

1. 开篇回答“为什么需要模式语汇”：它不是教你机械套模板，而是把反复出现、经受过验证的面向对象设计经验抽象成共享词典。
2. 这章的核心价值在于建立一个公共讨论面：团队不必每次都从零描述“怎么拆对象关系”，而可以直接讨论某种责任分配、协作结构、变化封装策略。

### 第2章 A Case Study: Designing a Document Editor

3. 官方目录明确给出一个“设计文档编辑器”的案例章，意味着作者不是直接罗列 23 个模式定义，而是先把模式放进真实系统设计问题里。
4. 对今天的软件工程读者来说，这章最值得迁移的不是某个旧式编辑器实现，而是“从需求、变化点、对象职责、协作关系逐步长出模式”的思维路线。

### 第3章 Creational Patterns

5. 创建型模式关注“对象如何被创建，而不把创建细节扩散到业务协作处”。
6. 本组 canonical patterns 包括：`Abstract Factory`、`Builder`、`Factory Method`、`Prototype`、`Singleton`。
7. 它们解决的问题不是单纯 `new` 不方便，而是当产品族、构造步骤、实例生命周期、依赖配置和平台差异都在变化时，如何把“创建变化”隔离出来。

### 第4章 Structural Patterns

8. 结构型模式关注“类与对象如何组合成更稳定、更灵活的结构”。
9. 本组 canonical patterns 包括：`Adapter`、`Bridge`、`Composite`、`Decorator`、`Facade`、`Flyweight`、`Proxy`。
10. 它们的共同目标是控制耦合：要么对齐接口，要么分离抽象和实现，要么统一部分/整体视图，要么在不改核心对象的前提下增加职责。

### 第5章 Behavioral Patterns

11. 行为型模式关注“对象之间如何协作、分发责任、表达算法与状态变化”。
12. 本组 canonical patterns 包括：`Chain of Responsibility`、`Command`、`Interpreter`、`Iterator`、`Mediator`、`Memento`、`Observer`、`State`、`Strategy`、`Template Method`、`Visitor`。
13. 这一组把系统从“对象已建好”推进到“对象如何说话与配合”：谁发起请求、谁决定流程、谁响应变化、谁承载算法扩展点。

### 第6章 Conclusion

14. 结论章可视为全书的方法论回收：模式不是终点，真正目标是提升可复用性、沟通效率、系统演进能力与设计判断力。
15. 它提醒读者把模式当作经验压缩包，而不是模式崇拜；是否使用某个模式，取决于变化压力、成本收益和系统边界，而不是名词收集。

### 附录与索引

16. `Glossary`、`Guide to Notation`、`Foundation Classes`、`Bibliography`、`Index` 表明本书不仅给概念，还提供术语、表示法和支撑材料，适合作为长期查阅型工具书。

## 12 条关键概念 / examples

1. **模式首先是沟通协议，不只是代码模板。** 它把复杂设计讨论压缩成可以复用的共同语言。
2. **模式来源于重复出现且被证明有效的问题-解法对。** 本书强调的是“成功设计经验的抽象”，不是发明新奇结构。
3. **创建型模式的核心是隔离变化中的构造逻辑。** 当对象创建依赖环境、配置、产品族和生命周期时，把创建从使用处抽离非常关键。
4. **结构型模式的核心是重新组织关系，而不是增加功能点。** 它们关注接口匹配、层次统一、职责叠加与访问控制。
5. **行为型模式讨论的是协作语义。** 真正难的常常不是对象本身，而是对象之间如何通知、调度、切换策略与表达流程。
6. **Program to an interface, not an implementation.** 虽然不同版本表述可能不同，但这本书最重要的迁移价值之一就是优先依赖抽象协作边界。
7. **Favor object composition over class inheritance.** GoF 的经典取向是尽量用组合换取更低耦合和更灵活的扩展能力。
8. **封装变化点，比封装一切更重要。** 模式之所以有用，是因为它们把未来最可能变化的部分隔离到了正确位置。
9. **Singleton 是受约束的生命周期工具，不是默认全局解法。** 它适合表达唯一实例，但也容易把依赖隐藏成全局耦合。
10. **Decorator 和 Proxy 都是“加一层”，但目的不同。** 前者偏职责增强，后者偏访问控制、延迟、缓存或保护。
11. **Observer、Strategy、Command 是现代前端/后端都高频出现的影子模式。** 事件系统、可插拔算法、动作对象化，今天仍然随处可见。
12. **本书真正训练的是设计判断力。** 背出 23 个模式不难，难的是识别什么时候值得抽象、什么时候继续保持简单。

## 23 个模式的速查分组 / retrieval scaffold

### 创建型（5）

- Abstract Factory：创建相关对象家族而不暴露具体类。
- Builder：分离复杂对象构建过程与表示。
- Factory Method：把实例化延迟到子类/扩展点。
- Prototype：通过复制原型创建对象。
- Singleton：保证一个类只有一个实例并提供统一访问点。

### 结构型（7）

- Adapter：让不兼容接口协同。
- Bridge：分离抽象与实现，两边独立变化。
- Composite：统一对待部分和整体。
- Decorator：动态附加职责。
- Facade：提供更简单一致的高层入口。
- Flyweight：共享内部状态，降低大量细粒度对象成本。
- Proxy：控制对真实对象的访问。

### 行为型（11）

- Chain of Responsibility：沿链路传递请求，直到某个处理者接住。
- Command：把请求封装成对象。
- Interpreter：用类层次表达语法与解释规则。
- Iterator：顺序访问聚合元素而不暴露内部表示。
- Mediator：把多对象网状依赖收拢到中介者。
- Memento：在不破坏封装前提下保存/恢复状态。
- Observer：一对多通知依赖。
- State：把状态相关行为局部化到状态对象。
- Strategy：把可替换算法封装成独立策略。
- Template Method：在父类定义算法骨架，把变动步骤延迟到子类。
- Visitor：把作用于对象结构的操作外置。

## 学习主线 / 推荐二刷顺序

1. 第一遍按官方目录阅读：先把 `Introduction` 与 `Case Study` 读成“问题空间与生长过程”，不要一上来就只背 23 个模式表。
2. 第二遍按三大分类重排：创建型 → 结构型 → 行为型，并为每个模式写一句“它主要隔离了哪一种变化”。
3. 第三遍做模式对照：哪些问题适合工厂/策略/观察者/装饰者，哪些只是普通函数抽取、模块拆分或对象组合，不需要上升到模式层级。
4. 第四遍输出一张自己的“反模式警戒表”：过度单例、继承滥用、事件泛滥、门面过厚、适配器层层嵌套，各自会把复杂度藏到哪里。

## 4 个实践练习

1. **练习 A：给现有前端 service 层做“创建变化隔离”**
   - 从一个同时负责创建 API client、拼装配置、执行请求的 service 开始，拆出工厂或 builder。
   - 验收：调用方不再关心具体构造细节；测试时可替换实现或注入 mock。

2. **练习 B：给 UI / hooks 系统画一张结构型模式地图**
   - 选择一个 React/Vue 项目，标记哪些位置是 adapter、facade、decorator、composite 的影子。
   - 验收：至少识别 4 个真实结构点，并说明它们分别在保护什么边界。

3. **练习 C：把一个交互流程重构成 Observer + Command + Strategy**
   - 例如表单提交流程：按钮动作命令化，请求成功/失败通过观察者分发，校验或提交流程通过策略替换。
   - 验收：动作可记录，UI 更新与执行逻辑解耦，策略切换无需改动主流程框架。

4. **练习 D：建立一个“模式不是目的”的审查清单**
   - 对一个你熟悉的模块做 review，逐项判断哪些复杂抽象值得保留，哪些只是为了“像模式”而存在。
   - 验收：至少删掉或否决 1 个过度抽象点，并写明理由（复杂度、耦合、测试成本、认知负担）。

## 对当前前端/后端/工程化能力的可落地应用点

**把 GoF 从“背名词”升级为“架构复盘语言”。**

- 对前端 React/Vue 工程：`Observer / Strategy / Decorator / Facade / Adapter` 可以直接映射到状态订阅、表单校验策略、埋点/缓存增强、BFF/SDK 包装层、旧新接口兼容层。
- 对后端服务设计：创建型模式帮助隔离对象装配与依赖注入，结构型模式帮助隔离网关/BFF/第三方集成边界，行为型模式帮助组织工作流、状态机、命令总线与审计动作。
- 对工程化与 AI 工作流：Command/Strategy/Chain of Responsibility/Mediator 尤其适合解释 task router、tool dispatch、hook pipeline、审核链和多代理协作边界。
- 对代码评审：以后看代码不只问“能不能跑”，还可以问“这里真正变化的维度是什么、当前抽象是否对应那个变化、有没有更便宜的组合替代”。
