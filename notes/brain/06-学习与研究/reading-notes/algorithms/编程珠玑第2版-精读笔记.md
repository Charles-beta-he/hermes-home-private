## 二、10条关键概念/例子（Key Concepts & Examples）

### 概念1：位向量排序（Bit-Vector Sort）
- **出处**: 列1 — Cracking the Oyster
- **问题**: 给定最多1000万个不重复正整数（每个≤10^7），在1.25MB内存限制下排序。
- **方法**: 用1个位表示一个整数是否存在。10^7位 ≈ 1.2MB，满足内存限制。初始化所有位为0，读入时置1，扫描输出。
- **核心洞察**: **问题定义（Requirement）比算法本身更重要。** 如果整数不重复且范围有限，位图就是最优解；如果允许重复或范围扩大，需要换策略。
- **适用场景**: 稠密整数集合的成员判定与排序、Bloom Filter 的思想原型。

### 概念2：循环不变式证明程序正确性
- **出处**: 列4 — Writing Correct Programs
- **方法**: 为循环定义一个不变式（init → invariant），证明每次迭代保持不变式（maintain），循环终止时不变式蕴含目标（terminate → postcondition）。
- **例子**: 二分查找的正确性证明——
  - 不变式：目标若存在，必在 a[l..u] 中
  - 初始化：l=0, u=n-1，覆盖全数组
  - 维护：根据 a[m] 与目标比较调整 l 或 u
  - 终止：l > u 时目标不存在，或 a[m] = target 找到
- **核心洞察**: 二分查找看似简单，但 Knuth 指出第一个无 bug 的二分查找发表花了17年。**不变式是写出正确程序的思维脚手架。**

### 概念3：后验估算（Back of the Envelope）
- **出处**: 列7 — The Back of the Envelope
- **方法**: 用简单算术和经验常数快速估算系统参数：
  - 2^10 ≈ 10^3（千），2^20 ≈ 10^6（百万），2^30 ≈ 10^9（十亿）
  - 磁盘寻道 ~10ms，内存读取 ~100ns，差10^5 倍
  - π秒 ≈ 10^7 秒/年（不到百万分之一误差）
- **Little定律**: 系统中平均顾客数 = 到达率 × 平均逗留时间（L = λW）
- **核心洞察**: **估算能力决定架构决策质量。** 能在白板上算出"这个方案需要多少带宽/内存/延迟"，就能在写代码前淘汰不可行方案。

### 概念4：问题重定义的力量
- **出处**: 列1 & 列12
- **例子**:
  - 列1: "排序1000万条记录" → "位向量标记1000万个整数" → 问题大幅简化
  - 列12: "在一个很长的文件中找到包含某模式的所有行" → 这就是 grep 的需求，不同的问题定义导向完全不同的解法
- **核心洞察**: **编程珠玑的核心哲学：正确的问题定义比聪明的算法更有价值。** 花时间理解问题的约束、输入规模、输出格式，往往能将 O(n log n) 问题降为 O(n) 甚至 O(1)。

### 概念5：算法设计的层次框架
- **出处**: 列8 — Algorithm Design Techniques
- **层次**: 问题 → 算法策略 → 数据结构 → 代码实现 → 系统集成
- **关键策略**:
  - **分治**: 归并排序、快速排序
  - **贪心**: 最小生成树、Huffman 编码
  - **动态规划**: 最长公共子序列
  - **增量/迭代**: 插入排序
- **核心洞察**: 选择算法策略时，**先考虑问题的数学结构（排序？搜索？优化？），再匹配策略，最后选数据结构和实现细节。**

### 概念6：性能优化的系统方法
- **出处**: 列6 — Perspective on Performance
- **步骤**:
  1. **需求定义**: 明确性能目标（"3秒内返回结果"）
  2. **粗估**: 用后验估算判断瓶颈在哪（CPU？IO？网络？）
  3. **Profile**: 用工具定位热点（80/20法则——80%时间花在20%代码上）
  4. **优化**: 从高层（算法）到低层（代码调优）逐级优化
  5. **验证**: 测量优化效果
- **核心洞察**: **不要猜，要量。** 性能优化的第一步永远是测量，不是直觉。

### 概念7：空间压缩的经典技巧
- **出处**: 列10 — Squeezing Space
- **技巧**:
  - **位压缩**: 用位域存储布尔标志（8个布尔值→1字节）
  - **稀疏结构**: 只存储非零元素（稀疏矩阵用三元组表示）
  - **数据压缩**: 行程编码、Huffman编码、字典编码
  - **代码压缩**: 用查表法代替复杂计算
- **核心洞察**: **空间和时间的权衡是工程决策的核心维度。** 嵌入式系统、大规模数据处理、移动端开发都需要空间敏感。

### 概念8：排序的工程选择
- **出处**: 列11 — Sorting
- **要点**:
  - 快排（Quicksort）：平均 O(n log n)，原地，但最坏 O(n²)
  - 归并排序（Merge Sort）：稳定，O(n log n)，需要额外空间
  - 堆排序（Heap Sort）：原地，O(n log n)，但缓存不友好
  - **工程实践**: 标准库排序几乎都是快排变体 + 小数组插入排序优化
- **核心洞察**: **理论最优 ≠ 实际最优。** 常数因子、缓存行为、实现复杂度在工程中比渐进复杂度更重要。

### 概念9：二分查找的变体家族
- **出处**: 列2 & 列4
- **变体**:
  - 基本二分查找（查找存在性）
  - 查找第一个/最后一个等于目标的位置
  - 查找第一个大于等于目标的位置（lower_bound）
  - 在旋转有序数组中查找
  - 二分答案（Binary Search on Answer）
- **核心洞察**: **二分查找不仅是"在一个有序数组里找数"，而是一种将 O(n) 搜索空间压缩到 O(log n) 的通用思维方式。** 任何满足单调性的问题都可以二分。

### 概念10：堆与优先队列的工程实现
- **出处**: 列14 — Heaps
- **要点**:
  - 二叉堆：数组表示完全二叉树，插入/删除 O(log n)
  - d-叉堆：增大 d 可以降低树高，减少比较次数
  - 可合并堆：左偏树、二项堆、Fibonacci 堆
  - **工程应用**: 任务调度、Dijkstra 最短路、Top-K 问题、合并 K 个有序流
- **核心洞察**: **选择堆实现时要考虑操作频率分布。** 如果 decrease-key 操作频繁（如 Dijkstra），Fibonacci 堆理论上更优；如果主要是 insert + extract-min，普通二叉堆的缓存友好性反而胜出。

## 三、3个实践练习（Practice Exercises）

### 练习1：实现位向量排序并对比标准排序
**目标**: 深入理解位向量排序的思想和适用条件。
**任务**:
1. 给定一个包含 N 个不重复整数的文件（N ≤ 10^7，每个整数 ≤ 10^7），分别用以下方法排序：
   - 方法A：标准库排序（如 Python sorted() 或 C++ std::sort）
   - 方法B：位向量法（bitmap sort）
2. 比较两种方法的：
   - 内存使用
   - 运行时间
   - 代码行数
3. 测试边界条件：N=1, N=10^7, 整数稀疏（最大值远大于N） vs 稠密（最大值≈N）
**预期收获**: 理解"问题约束如何导向最优算法"，以及位图在稠密整数场景下的巨大优势。

### 练习2：用循环不变式证明一个算法的正确性
**目标**: 掌握循环不变式的证明方法。
**任务**:
1. 选择以下算法之一：
   - 插入排序
   - 快速排序的 partition 函数
   - 求数组最大子数组和的 Kadane 算法
2. 写出完整的循环不变式证明：
   - 初始化（Init）：循环开始前不变式成立
   - 保持（Maintain）：每次迭代后不变式仍成立
   - 终止（Terminate）：循环结束时不变式蕴含目标
3. 故意引入一个 bug（比如 off-by-one），观察不变式在哪一步被违反
**预期收获**: 培养"写代码前先想清楚不变式"的习惯，减少调试时间。

### 练习3：后验估算实战——设计一个系统
**目标**: 练习"信封背面"估算能力。
**任务**:
假设你要设计一个类似 Twitter 的短消息系统，估算以下参数：
1. 每天产生多少条消息？（假设日活用户数 × 每人每天发帖数）
2. 每条消息多少字节？（文本 + 元数据）
3. 每天存储需求是多少 TB？
4. 读写比大约是多少？（考虑 Timeline 聚合的读放大）
5. 如果要支持1000万用户同时在线，需要多少台服务器？（假设每台服务器处理1万连接）
6. 用 Little 定律估算：用户平均浏览 Timeline 的逗留时间 vs 系统需要同时维持的连接数
**预期收获**: 培养在架构设计会议中快速估算、判断可行性的能力。

## 四、可落地应用点（Practical Application）

### 应用：将"后验估算"能力集成到项目/技能树

**背景**: 在日常工程工作中，我们经常面临快速判断方案可行性的场景：
- "这个功能的存储需求会不会超出预算？"
- "这个 API 的 QPS 上限是多少？"
- "引入这个中间件会增加多少延迟？"

**落地方案**: 创建一个"后验估算速查表"技能（Skill），包含：
1. **常用常数**: 磁盘寻道、网络 RTT、内存读写、CPU 周期等基准值
2. **快速计算模板**: Little 定律、排队论基本公式、带宽-延迟乘积
3. **常见架构的规模参考**: 1M DAU 的社交系统、10K QPS 的电商秒杀等
4. **检查清单**: 在做架构决策前，用3分钟快速估算验证可行性

**与当前能力树的连接**:
- 与 `api-and-interface-design` 技能配合：API 设计时估算 payload 大小和带宽需求
- 与 `devops` 技能配合：部署规划时估算存储和计算资源
- 与 `codebase-intelligence` 技能配合：代码审查时识别潜在的性能瓶颈

**实施步骤**:
1. 在 `~/.hermes/skills/` 下创建 `back-of-envelope-estimation` 技能
2. 包含常数速查表、估算模板、真实案例
3. 在架构设计和方案评审流程中引用该技能

## 五、核心语录（Memorable Quotes）

1. "When in doubt, use brute force." —— 当拿不准时，用暴力法（先保证正确，再优化性能）
2. "Careful analysis of a small problem can pay huge dividends." —— 深入分析小问题，能获得巨大回报
3. "The first step in optimization is to measure." —— 优化的第一步是测量
4. "Never optimize until you know you need to." —— 除非确认需要，否则不要优化
5. "A good algorithm is like a sharp knife: it does one job very well." —— 好算法如利刃，做好一件事
