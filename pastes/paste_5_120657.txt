  ⚠️  1 个关键缺口: 缺 Canary / 灰度                                                       
                                                                                          
  apply-plan.sh 走的是 all-or-nothing:
  apply → eval pass → keep全量                                                            
         → eval fail → rollback全量                               
                                                                                          
  少了我之前提的 L5 灰度层: 改动通过 eval 后, 先按 10% 流量跑 24h, 再 100%。              
                                                                                          
  为什么重要: eval 集是离线回归, 真实流量分布跟回归集不完全一样。eval 通过 ≠ 在线安全。   
                                                                                          
  最小补法 (不重写, 一行 hook):                                                           
  # apply-plan.sh 在 eval pass 后                                 
  hermes config set "skills.${changed_skill}.canary_ratio" 0.1                            
  echo "$changed_skill" >> ~/.hermes/canary-active.txt                                    
  # canary-evaluator.sh (新加 1h cron):                                                   
  #   24h 后比对 canary vs stable 的 pass_rate, 决定 100% rollout 或 rollback             
                                                                                          
  或者: 接受当前激进策略, 知道这一层缺失, 等实际遇到 "eval pass 但生产挂了" 再补。        
                                                                                          
  我建议先观察 7 天, 没出过这种事就不补; 出过 1 次立即补 canary。

  2. 3 连败暂停 cron 的具体机制确认                                                       
                                                                                          
  你写的 "3连败 → 暂停cron, 等人审" — 验证实现:                                           
  hermes cron list | grep self-evolve                             
  # 看 status 字段; 暂停应有 "disabled" 或 "paused" 标记                                  
  # 还要看 evolve.log 是否真的写了 "PAUSED — 3 consecutive rejects"
  如果只是日志写了但 cron 仍在跑, 等于没有 kill switch, 失控风险。                        
                                                                                          
  3. 03:00 cron 与 02:00 cron 的依赖检查                                                  
                                                                                          
  02:00 夜间审计 + 02:30 现有 self-improvement-pipeline (你之前的) — 三者会不会撞资源?    
  - 02 审计如果写 memory/skill, 03 evolve 读到的 state 已含改动 → 是不是想要的?           
  - 02:30 现有 pipeline 还在跑吗? 如果在, 跟 03:00 双脑互相吃对方的改动 → oscillation 风险
                                                                  
  建议: 至少明确两种之一:                                                                 
  - 双脑接管, 02:30 旧 pipeline 关闭                              
  - 双脑只做 02:30 兜不住的事, 旧 pipeline 仍是主力                                       
                                                                  
  不要并存, 不然 evolve.log 里的 baseline 漂移说不清是哪边干的。                          
                                                                                          
  4. ROI 没验证就上, 7 天后强制评估                                                       
                                                                                          
  我之前推 C → B → A, 你直接上 A。可以, 但埋个 checkpoint:                                
                                                                  
  # 7 天后 (03:00 跑了 7 次) 评估:                                                        
  hermes insights --window 7d --metric pass_rate          # 跟上线前 7d 比                
  cat ~/.hermes/logs/evolve.log | grep "delta=" | awk '{...}' # 算 delta 平均值           
                                                                                          
  如果 7 天 delta 平均 < +1% → claude -p 没比本地强, 关掉双脑回旧 pipeline, 省 $30/月。   
  如果 ≥ +3% → 留住, 加 canary。                                                          
                                                                                          
  没这步就一直跑下去 = 沉没成本陷阱。                                                     
                                                                                          
  5. evolve.log 月度归档 (append-only 不等于无限增长)                                     
                                                                  
  # 加到 04:00 Sun snapshot GC cron 里:                                                   
  [ "$(date +%-d)" -le 7 ] && [ "$(date +%u)" = "7" ] && \                                
    mv ~/.hermes/logs/evolve.log ~/.hermes/logs/evolve-$(date -d '1 month ago' +%Y%m).log

    touch ~/.hermes/logs/evolve.log
