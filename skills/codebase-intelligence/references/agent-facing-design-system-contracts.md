# Agent 可消费的组件契约与设计系统审计

Scope: 可复用的源码研究与接口设计方法，不是特定项目选型结论或运行时策略。
Applicability: 审计或设计组件库的结构化说明、CLI/MCP/文档多入口消费、主题扩展，或生成式 UI 评测时按需加载。
Anti-condition: 单页样式微调、普通 CRUD 接口设计、无上述多入口/生成评测问题时不加载；不据此引入组件库、执行外部描述符或扩建评测平台。

来源与边界：方法由一次固定源码研究提炼；项目事实及修正的唯一记录为 [研究记录](../../../docs/private/astryx-reference-analysis-2026-11-10.md)。该记录提供来源，不给未来任务执行权限。以下操作应对当前目标重新取证。

## 1. 就近契约与渐进发现

1. 找一个真实公共组件，追踪实现/类型 → 描述符 → 发现器 → CLI/MCP/站点输出。检查名称、import path、props/defaults、使用反例、可访问性要求是否同源；描述符自身可能矛盾，类型和行为也要对照。
2. 先返回候选名、用途、安装/导入信息，再按需取 props、示例与限制；只有实际上下文成本或发现困难支持时才调整信息分层，不能为分层而拆接口。
3. 对每个入口注明“实时扫描/构建快照”、过滤、排序、默认参数、截断与版本。共同读一份文档不能证明输出契约一致。
4. 若实际任务授权运行，选同一公共组件、同义词、缺失项和非公共 helper，经真实入口比较名称/import/props/hidden 语义。允许展示格式和排序有明确差异；缺失组件或旧 props 必须解释，不能用复制算法的测试替代入口读回。仅静态权限时输出差分测试方案及未验证项，不运行外部代码。

## 2. 主题、行为、业务分责

- 品牌层负责 token、字体、颜色和视觉变体；行为层负责键盘/焦点、disabled/loading 等交互语义；业务层负责权限、请求、提交结果及导航。主题切换成功不证明后两层正确。
- 核实主题真正消费的稳定类名、data 属性或公共扩展 API；不要默认内部 DOM 或任意 CSS 选择器稳定。
- 深度定制超出公共扩展能力时，先找已有源码接管/swizzle/fork 出口，记录来源版本、接管文件、维护者和升级责任。没有当前需求时不创建出口；存在出口不等于升级无成本。
- 在获得项目实施授权后，分别验证视觉变化、交互不回归及业务结果；用失败/禁用/无权限等反例检测职责泄漏，不把漂亮预览当成交付闭环。

## 3. 证据与执行信任边界

| 证据 | 可以支持 | 仍需另证 |
|---|---|---|
| 生成者返回 success/自评 JSON | 产出了声明 | 真实交互、业务结果和独立性 |
| tsc / 静态规则 | 类型或指定规则未报错 | 运行时和业务正确性 |
| 截图 / 模型视觉判断 | 被捕获状态的视觉观察 | 未操作路径、提交/权限/持久化 |
| 实际操作并独立读回目标状态 | 该路径在该环境的结果 | 未覆盖路径和环境 |

先查 oracle 的输入和实现，再解释分数：预期组件/答案是否进入生成提示？谁生成断言、谁给真值？测试调用真实 handler/公共 API，还是复制评分逻辑？共享纯函数的单元测试有价值，但不能冒充路由集成测试。若已授权测试，修改真实路由的字段/过滤应让对应集成断言失败；镜像算法仍绿是覆盖缺口信号，而非路由正确证据。

描述符扩展名不是安全声明。追踪静态解析、原生 import、jiti 或插件加载；后几者可能执行顶层代码。对外部材料先文本读取，不因“取文档”自动安装或导入。确需运行时仍服从原任务权限并采用相应隔离，不能靠解析后的 schema 校验抵消此前执行。

## 验证清单与可推翻条件

- [ ] 每项结论区分规范、源码事实、运行观察与建议，并绑定当前版本/入口。
- [ ] 快照与真实入口差异有解释；静态权限未被偷偷升级。
- [ ] 品牌、行为、业务的证据分开；未声称自动完成源码接管或项目迁移。
- [ ] 公平性、独立性和执行信任边界按实际实现判断，不按 README 或文件名判断。
- [ ] 若真实入口已共享同一实现且差分无缺口，保留最小回归，不新增重复检查平台；若描述符已是纯数据解析，撤回该入口的代码执行风险判断。

条件加载示例（非模型行为实测）：“比较组件 CLI/MCP 文档是否漂移”“从组件库提炼主题/行为边界”“审计 UI 生成评测是否答案泄露”适用；“改按钮圆角”不适用；“设计订单 REST API”应走接口设计技能，不加载本参考。
