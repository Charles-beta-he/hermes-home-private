## PWA primary wrapper

`src/services/auth.service.ts`:

- `verifyPaymentPassword(password)` posts to `/auth/pin/verify`; axios baseURL makes this backend `POST /api/auth/pin/verify`.
- Body is generated by `encField(password, 'encPin', 'pin')`.
- Runtime shape is either `{ encPin: <RSA-OAEP base64> }` or fallback `{ pin: <plain 6 digits> }`.
- At capture time, PWA did not send `type` for this wrapper and normally did not send `purpose`.

`src/lib/pinCrypto.ts` is the source of dual-field behavior. It loads `/crypto/pin-key`, encrypts with Web Crypto RSA-OAEP SHA-256, and falls back to plaintext for availability.

## Direct PWA callers of `verifyPaymentPassword`

Production direct callers found:

1. `src/screens/payment/PaymentVerifyScreens.tsx` — route `/pay/verify/pin`; global payment PIN gate.
2. `src/screens/auth/VerifyPinOnLoginScreen.tsx` — route `/verify/pin`; untrusted-device login second factor.
3. `src/screens/remit/RemitPasswordScreen.tsx` — route `/remit/:payeeId/pay`; older remit PIN→SMS flow.
4. `src/screens/card/CardCvvScreen.tsx` — route `/card/cvv`; verifies PIN, then calls secure card info with payment PIN.
5. `src/screens/me/ChangePaymentPwdScreen.tsx` — route `/me/payment-pwd`; verifies old PIN before changing PIN via `/auth/pin/change`.

There is also `src/lib/pinVerify.ts`, a low-level/test helper that posts `{ pin }` to `/auth/pin/verify` when `VITE_API_BASE` is set. Do not treat it as the production wrapper unless imports prove active use.

## `/pay/verify/pin` transitive coverage

Many flows do not call the wrapper directly. They navigate to `/pay/verify/pin`, which then calls `/auth/pin/verify`, stores `paymentPin` in router state, optionally continues to `/pay/verify/code`, and finally submits the business API.

Common entry sources:

- Exchange: `screens/exchange/ExchangeConfirmScreen.tsx` → later `exchangeService.execute` → `/exchange/confirm` with `encPaymentPin/paymentPin`.
- Payout crypto/CNY: `screens/payout/*` → later `payoutService.payout` → `/payout/usdt` or `/payout/cny` with `encPaymentPin/paymentPin`.
- Remit: `screens/remit/RemitPreviewScreen.tsx` → later `remitService.execute` → `/remit/execute` with `encPin/pin`.
- Wealth buy/redeem: `screens/wealth/*`, `screens/card/CardFixed*` → later `/wealth/purchase` or `/wealth/holdings/{id}/redeem` with `encPin/pin`.
- Card topup/withdraw/reset PIN/fixed products: `screens/card/*` → later card/wealth/payment APIs with `paymentPin` or encrypted variant.
- Device/security sensitive operations: e.g. `screens/me/security/DevicesScreen.tsx` can enter `/pay/verify/pin`.

Interpretation: `/api/auth/pin/verify` is a broad front-door step-up gate in UVISA, but final money-moving APIs generally still receive PIN/MFA and perform their own verification. Do not claim it is the only verifier for funds movement.

## Backend contract evidence

Backend legacy endpoint:

`api/api-public/src/main/java/com/uvisa/api/pub/LegacyApiController.java`

- `@PostMapping("/api/auth/pin/verify")`
- DTO: `PinVerifyRequest(String pin, String encPin, String purpose)`
- Verifies via `paymentPinService.verify(userId, pinCrypto.resolve(req.pin(), req.encPin()))`.
- `purpose="phone-rebind"` marks `PhoneRebindStepUpService` Redis flag.

Backend ME-domain endpoint:

`api/api-public/src/main/java/com/uvisa/api/pub/MeController.java`

- `@PostMapping("/payment-pin/verify")`
- DTO includes `pin`, `encPin`, `purpose`.
- Also recognizes `purpose="phone-rebind"`.

Backend docs: `docs/api/auth-pin-verify.md` documents only `pin`, `encPin`, `purpose` for `/api/auth/pin/verify`. If a task screenshot/spec mentions a new `type` field such as `exchange` or `payout`, verify whether backend DTO/docs have been updated before assuming it is live. In the captured state, neither PWA nor backend legacy DTO consumed `type`.

## RN migration/mobile notes

In `apps/mobile`:

- `src/services/nativeBackend.ts` uses `/auth/pin/verify` for native deep-feature T2 card CVV readiness and currently sends `{ pin: paymentPin }` under TLS until native RSA bridge is added.
- `src/services/authFlowService.ts` also posts `/auth/pin/verify` with `{ pin }`.
- No `type` or `purpose` was found in RN mobile PIN verify calls in the captured state.

## Recommended analysis workflow

1. Search the wrapper first: `verifyPaymentPassword`, `verifyMyPaymentPin`, `/auth/pin/verify`, `/me/payment-pin/verify`.
2. Then search route-level fan-in: `/pay/verify/pin`, `/verify/pin`.
3. For broad coverage, classify both direct callers and transitive router-state flows.
4. Inspect final business APIs receiving `paymentPin`, `encPaymentPin`, `pin`, or `encPin`; distinguish pre-gate from final authorization.
5. Inspect backend controller/DTO/docs before accepting newly mentioned fields (`type`, `purpose`) as supported.
6. Report with evidence as `file:line`, separating current behavior from proposed contract changes.
