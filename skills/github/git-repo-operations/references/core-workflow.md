## Core Workflow

1. **Discover state**: `git status --short --branch`, current branch, upstream, and dirty files.
2. **Resolve the target**: for project work, read the project profile and map repo role → target branch. Do not assume `main`/`master`/same branch for every repo.
3. **Fetch before acting**: `git fetch origin --prune` before checkout, rebase, or branch creation. If fetch fails at the transport layer (SSH banner closed, DNS/proxy timeout, VPN/TUN failure), stop branch freshness claims there: report the network boundary, label any `origin/*` data as cached-local evidence, and do not create long-lived task branches or release/merge decisions from stale refs unless the user explicitly accepts that risk.
4. **Classify operation**:
   - conflict resolution: merge/rebase/stash markers and semantic merge
   - branch orchestration: sync/check/create/rebase multiple repos
   - release/PR readiness: verify remote parity and required tests
5. **Resolve mechanically, verify semantically**: remove markers and stage files, then run the relevant build/test/typecheck slice.
5. **Push safely**: after rebase, use `--force-with-lease`; never blind `--force`.
6. **Scope commits in live-state repos and shared JSON/i18n files**: when a repository contains scheduler/runtime state files that drift during normal operation (for example cron job counters, next-run timestamps, logs, caches), or a shared data file already has unrelated dirty hunks (for example locale JSON keys from another task), do not stage the whole dirty file just because one durable config field/key changed. Build a staged blob from `HEAD:<file>` with only the intended semantic edit, or otherwise stage a minimal patch, then verify `git diff --cached` contains only that scoped change. Leave live runtime drift/unrelated hunks unstaged. For heavily dirty skill/docs/JSON/i18n files where one new durable line/key must be committed without absorbing unrelated working-tree churn, construct a clean blob from `git show HEAD:<path>` plus the intended insertion, write it with `git hash-object -w`, stage it with `git update-index --cacheinfo <mode>,<blob>,<path>`, then inspect `git diff --cached` before committing. After committing, run a path-limited `git diff HEAD -- <path>` to verify the unrelated hunks still remain only in the working tree and were not smuggled into the commit.
7. **For user-authorized “推进到边界” work, still commit only the intended slice**: before committing, run status/diff checks, stage exact touched files only, inspect `git diff --cached --stat` and `git diff --cached --name-only`, and explicitly leave unrelated untracked/dirty files unstaged. If verification passes, make the scoped commit; if the next action would enable broad runtime execution, lifecycle mutation, external writes, or other privileged authority, stop and report the boundary instead of silently expanding the commit/task scope.
8. **For submodule operations, verify metadata before claiming recursive health**: if recursive submodule status fails because a tracked gitlink has no mapping, restore the mapping from the tracked path, expected commit, and known remote URL when available. Do not delete backup/history directories just to make recursion pass; make the metadata repair auditable, then rerun the recursive check.
9. **When committing scoped submodule work from a dirty child repo, separate gitlink pinning from child dirtiness and pre-existing parent index state**: commit the intended files inside the child first. In the parent, inspect `git diff --cached --name-only` *before* staging the gitlink; if unrelated files are already staged, unstage or stop rather than mixing them into the pointer commit. Then stage only the submodule pointer plus any explicitly intended parent-level files, re-check `git diff --cached --stat --submodule=short` and `git diff --cached --name-only`, and commit only if the cached diff contains the intended slice. If an accidental parent commit already mixed unrelated staged files with the gitlink, make a corrective follow-up commit that restores those unrelated paths from the previous commit while preserving the gitlink, then verify the net diff from the prior good parent contains only the submodule pointer. If `git status` still shows `m <submodule>` because unrelated child files remain dirty, disclose that as pre-existing/unrelated child dirtiness rather than trying to clean or stage it. Do not stage ignored runtime state such as cron DB/job counters or rollback backups just to make parent status clean.
10. **When clearing mixed control-plane homes, distinguish shared policy from local overlay**: commit `.gitignore`/`git rm --cached` migrations for durable runtime/secret boundaries, but use repo-local `.git/info/exclude` for huge machine-specific overlays that should not become shared policy. A clean status can legitimately mean "tracked state clean; local overlay ignored and kept on disk" — disclose that distinction. When整理 local existing state, classify durable skills/scripts/docs separately from runtime/cache/backups/raw evidence, run targeted tests for committed scripts, and if hooks flag secret-like false positives in otherwise useful files, reset or sanitize those paths and report the redaction/landing-zone boundary instead of bypassing hooks. In evidence/docs, prefer neutral wording such as `private-auth material`, `redacted provider key field`, or `quota units` over staged variable names that hooks intentionally treat as high risk (for example token/key/secret-style field labels). If a hook scans ignored high-risk config (for example local config with inline API headers), migrate the secret to an ignored env/vault placeholder, verify runtime interpolation, then commit only the intended tracked files; see `references/secret-scan-safe-scoped-commits.md`.
10. **For PRs/MRs from dirty, shared, or stale worktrees, isolate the branch before commit/merge**: export the intended diff to a patch, create a clean temporary worktree from the true base (`git worktree add -b <branch> /tmp/<repo>-pr origin/<base>`), apply only the scoped patch or cherry-pick only the intended commit(s), install/build/test there, then commit/push/PR/MR from that clean worktree. This prevents unrelated local changes, Finder/copy artifacts such as `* 2.*`, active runtime state, or target-branch drift from leaking into the review. Before creating the review, verify the requested target branch exists as a live remote ref/API branch; if a user says `dev` but only `develop`/`dev-*` exists, stop or apply their explicit correction rather than inventing a target. See `references/clean-gitlab-mr-from-dirty-stale-worktree.md`.
10a. **If a scoped commit was accidentally made on the target branch but the user wants PR/MR flow, move the commit instead of pushing target**: create or update a feature branch at the current commit, reset the local target branch back to `origin/<target>` (after fetching if possible; label cached refs if fetch fails), checkout the feature branch, verify `git rev-list --left-right --count origin/<target>...<feature>` shows only the intended ahead commits, then push/create the PR/MR from the feature branch. If push/API fails, stop at the network/auth boundary and report the prepared branch plus exact resume command; do not leave the local target branch ahead or silently direct-push.
11. **When extracting gains from a dirty stale workspace, classify before applying**: compare the dirty worktree to the freshly fetched target branch, back up tracked/untracked state, and classify changes as already-in-target, superseded-by-target, stale duplicate/junk, beneficial increment, or needs-human. Extract only the beneficial increment into a clean worktree from `origin/<target>`, preserving newer target semantics. Finder-style duplicate files such as `* 2.tsx` are evidence of copied stale snapshots, not automatic gains. See `references/dirty-workspace-gain-extraction.md`.
12. **For commit-scoped removal requests, remove the commit’s semantic footprint, not the whole surrounding feature**: first inspect `git show --stat --name-status <commit>` and path-limited diffs to identify exactly what the commit introduced. In a dirty repo, create a clean worktree from the current target ref, then delete/revert only that commit’s UI, i18n, tests, and gating semantics. Search for residual strings/test IDs from the removed commit, update surviving tests to assert the intended underlying behavior, and verify focused tests + build/full suite before committing. Do not use broad `git revert` if later commits intentionally built adjacent behavior on top; manually preserve later target-branch semantics.
13. **When enabling GitHub auto-merge from a repo with multiple worktrees, avoid implicit local checkout operations**: `gh pr merge <n> --auto ...` may try to inspect/check out the base branch and fail if that branch is already checked out in another worktree (`fatal: '<base>' is already used by worktree ...`). Retry from a neutral cwd with explicit repo targeting: `gh pr merge <n> --repo OWNER/REPO --auto --squash --delete-branch`, then verify with `gh pr view <n> --repo OWNER/REPO --json state,autoMergeRequest,mergedAt,statusCheckRollup`.
13. **When the user says “auto-merge this PR into <branch>”, treat target branch and repository policy as gates, not assumptions**: inspect the PR, retarget it only if the user explicitly names a different base, then read back `mergeable/mergeStateStatus`. If GitHub returns `Auto merge is not allowed for this repository (enablePullRequestAutoMerge)`, do not stop after the failed `--auto` call when the user’s goal is clearly to land the PR; if the PR is mergeable and checks are acceptable, use the normal merge command and verify the merged state. If retargeting makes the PR conflicted, create a clean temporary worktree from `origin/<target>`, fetch `pull/<n>/head`, run `git merge --no-commit --no-ff`, resolve conflicts semantically while preserving target-branch behavior, run the focused tests for touched files, push the conflict-resolution merge commit back to the PR head, re-check PR diff/name-only, then merge. Clean up the temp worktree and disclose any repo-policy fallback from auto-merge to manual merge. If there is no existing PR and the user wants the current change landed to a shared target, create the PR from a clean worktree rooted at `origin/<target>`; transplant only the intended semantic hunks and keep the target branch’s existing layout/runtime/test contracts as the base truth. Avoid copying whole dirty files from another branch when the target has already evolved adjacent contracts. Run the target branch’s own build gate in that clean worktree; if it exposes a pre-existing unrelated target blocker, either stop and report it or add only the smallest gate-unblocking fix needed to land the user-authorized PR, with explicit disclosure in the PR/final report. `gh pr create` may not support `--json` on older GitHub CLI versions; create first, then use `gh pr view --json ...` for readback.
14. **Feature-flagged endpoint PRs need trigger proof before merge.** Applicability: PR review/merge for any client/frontend branch that adds a call to a server endpoint gated by a build-time/runtime feature flag or deploy-time environment variable. Anti-condition: do not use this to assert authenticated business success, data correctness, or production readiness without a real authorized session and the project’s normal acceptance gates. In a clean PR worktree, build/test with the relevant flag explicitly enabled and search the built artifact for the endpoint or durable trigger marker to prove the code path is compiled and not tree-shaken/disabled. Probe the live/backend route without secrets when possible: an unauthenticated `401` or `403` response from the expected path is route/auth evidence and is stronger than a `404`/proxy miss, but label it as unauthenticated route evidence only. After explicit merge authorization, run `gh pr merge <n> --repo OWNER/REPO ...` from a neutral cwd to avoid dirty/multi-worktree checkout side effects, then read back `gh pr view` plus remote-target evidence (`git ls-remote` or fresh fetch) showing the target branch at the merge commit.
