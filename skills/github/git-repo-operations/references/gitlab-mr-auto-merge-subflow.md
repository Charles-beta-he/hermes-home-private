## GitLab Self-Managed MR / Auto-Merge Subflow

Applicability: use when a project is hosted on a self-managed GitLab instance and the user wants automated MR creation, merge-readiness checks, or auto-merge. Anti-condition: do not encode concrete hosts, project paths, branch names, or tokens here; resolve them from the current repo and GitLab API each time.

1. **Credential boundary first.** Never extract browser cookies/localStorage/session tokens, and do not use tokens pasted into chat. Ask the user to create/revoke PATs in the GitLab UI and load them into `glab` via stdin/keyring (`pbpaste | glab auth login --hostname <host> --stdin --git-protocol ssh --use-keyring`) so the token does not enter transcripts or shell history. If a token was pasted in chat, treat it as leaked and have the user revoke/regenerate it before proceeding.
2. **Self-managed OAuth may need admin setup.** `glab auth login --web` can fail on self-managed GitLab with `Set 'client_id' first...`; that means the instance has not configured an OAuth application for glab. Fall back to a PAT stored in keyring, or have an admin configure `client_id` with `glab config set client_id <id> -g --host <host>`.
3. **Verify auth with API, not only token presence.** `glab auth status` can show “Token found” while `/api/v4/user` returns 401. Require `glab api user` or equivalent `/api/v4/user` success before using MR/merge commands.
4. **Read project policy before proposing auto-merge.** Use `glab api /projects/<urlencoded-path>` and protected-branch endpoints to capture access level, default branch, MR enabled, jobs enabled, merge method, `only_allow_merge_if_pipeline_succeeds`, discussion/approval gates, source-branch removal, and protected branch merge/push levels. Treat a configured token plus SSH fetch as insufficient evidence.
5. **Probe merge automation safely.** If the user authorizes capability testing, create temporary target/source branches from a non-production base, create a temporary MR into that temporary target branch, attempt `glab mr merge --auto-merge`, then read back MR fields (`state`, `merged_at`, `detailed_merge_status`, `merge_when_pipeline_succeeds`) and delete all probe branches/worktrees. Do not test directly against shared integration or release branches.
5a. **Create review MRs with explicit descriptions and readback.** `glab mr create` flag support varies by version; if `--description-file` is unavailable, pass `--description "$(cat <file>)"` or use the GitLab API. After creation, read back the MR through `glab mr view` and/or `/projects/<encoded>/merge_requests/<iid>` and verify `state=opened`, expected source/target branches, `merge_when_pipeline_succeeds=false` when auto-merge is not authorized, conflict status, pipeline fields, and head SHA before reporting the MR ready.
6. **No pipeline means auto-merge may merge immediately.** On GitLab, `glab mr merge --auto-merge` may report no pipeline and merge immediately when project settings do not require successful pipelines. If the desired invariant is “merge only after build/test passes,” add/enforce CI first rather than relying on auto-merge semantics.
7. **Report capability levels separately.** Distinguish: can authenticate; can create MR; can read MR/policies; can merge non-protected temporary target; can merge protected branch by permission; can auto-merge after CI gate. Do not collapse these into “auto-merge works.”
