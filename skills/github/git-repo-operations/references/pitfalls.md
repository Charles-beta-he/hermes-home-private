## Common Pitfalls

1. **Treating every repo as if it shares the same target branch.** Resolve per repo role.
2. **Resolving conflicts by side instead of meaning.** Read both changes and preserve semantics.
3. **Forgetting stash-pop semantics.** `--ours`/`--theirs` differ from rebase mental models.
4. **Leaving conflict markers.** Search for `<<<<<<<`, not just `=======`.
5. **Force-pushing unsafely.** Use `--force-with-lease` only after verifying the branch.
6. **Revert can restore stale lines.** Diff reverted files and verify semantics, not just type correctness.
7. **Auto-merge command fails because of sibling worktrees.** Do not delete or disturb the sibling worktree just to satisfy `gh`; rerun the merge command with `--repo OWNER/REPO` from a neutral directory and verify PR state afterward.
8. **Patch application from an old dirty branch can silently omit, conflict with, or revert target-branch behavior.** If the PR target is not the source branch's base (for example user asks for PR to `test` while the local dirty branch drifted from another branch), do not build the PR from a broad `git diff origin/<target>` taken in the dirty worktree. First inspect the target tip for affected files, then create the PR worktree from the requested target ref and apply only the minimal semantic addition. Preserve target-branch behavior as SSOT and avoid replacing newer target helpers/filters with older local versions. If the target already has an adjacent evolved contract (for example a store action now returns `{ ok, txId, message }` for one flow while the dirty branch uses `{ success, txId }`), adapt only the missing semantic fix to the target contract instead of forward-porting the dirty branch's older API shape. After applying the patch, compare `git diff --stat`, `git diff --check`, and the named files against the original intent before committing; verify line-start conflict markers are gone.
8a. **When the user asks to整理代码 from a clean `test`/staging branch, start with a clean worktree from the remote target before copying anything.** Run `git fetch --prune`, create `git worktree add -b <topic> <clean-path> origin/<target>`, then inspect whether the target already contains the intended fix. If the clean branch is 0/0 ahead-behind and the verification passes, do not manufacture a duplicate commit or push an empty branch just to satisfy the task wording; report that the target already has the fix with test/build evidence. Leave the original dirty workspace untouched.
9. **Target-branch test contracts outrank source-branch assumptions.** A clean build/test on the original working branch is not enough when landing to another integration branch. Run the target branch’s focused tests and full gate inside the clean PR worktree. If the target already contains adjacent contracts (for example product pre-permission prompts around a device API), adapt the new implementation to preserve those contracts instead of deleting or weakening them to match the source branch’s older behavior.
10. **When forward-porting UI/PWA fixes across branch families, re-diagnose against the target tip instead of replaying the previous branch patch.** The target branch may already contain an equivalent geometry/layout fix under different tokens. In that case, preserve the target's established tokens/tests and add only the missing trigger guard (for example an iOS standalone `color-scheme` override that prevents WebKit safe-area/env recomputation during app theme switches) rather than replacing the target branch's newer TabBar/safe-area model. For input/keyboard/layout fixes, search the clean target worktree for the target's actual input variants (for example shared input component usages plus hand-written `inputMode="decimal"` fields) before transplanting; target-only pages may need the same semantic marker, while source-only UI reshapes (such as a different FAQ/search design) should be left out of the PR.
10. **Auto-merge can merge immediately, not just queue.** After `gh pr merge --auto ...`, always read back `gh pr view <n> --json state,autoMergeRequest,mergedAt,mergeCommit,statusCheckRollup`. If `state=MERGED` and `autoMergeRequest=null`, the PR met requirements and merged immediately; report merged evidence rather than saying auto-merge is merely enabled.
10a. **`gh pr merge` local update output can overstate PR scope.** When merging from a temporary worktree whose local base branch is behind `origin/<target>`, GitHub CLI may fetch/fast-forward the local checkout and print the whole target-branch delta, including files from earlier merged PRs. Do not use that stdout as the PR scope. Verify the actual merged PR with `gh pr view <n> --json files,additions,deletions,commits,mergeCommit,state,mergedAt` and, when needed, `git show --name-only <mergeCommit>` or `git diff <preMergeTarget> <mergeCommit>` before reporting changed files.
11. **Private-repo install paths must not assume a GUI, browser, or GitHub CLI.**
10. **Stale local branches can fabricate a sync need.** For branch synchronization decisions, compare freshly fetched remote refs (`origin/source...origin/target`), not local `source`/`target` branches that may be behind or checked out in another worktree. Verify ancestry with `git merge-base --is-ancestor origin/<source> origin/<target>` and direct remote tips with `git ls-remote` when the user suspects new remote commits.
10. **Do not open no-op sync PRs.** If the source branch is already an ancestor of the target branch, a clean worktree merge will be `Already up to date` and the candidate branch will be `0 0` ahead/behind the target. Stop and report the no-op evidence instead of pushing an empty branch or creating an empty PR.
11. **Private-repo install paths must not assume a GUI, browser, or GitHub CLI.** For private source distributions, document at least three token-safe paths: GitHub CLI/device-code login when available, headless SSH/deploy-key clone for servers or containers, and an existing-checkout/offline-transfer finalizer. Never ask users to put a token in a clone URL or make `curl | bash` from a private raw URL the only primary path.
