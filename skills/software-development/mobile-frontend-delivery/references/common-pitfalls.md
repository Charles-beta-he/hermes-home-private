## Common Pitfalls

1. **Treating PWA as one cache layer.** Browser cache, service-worker cache, CDN cache, and OS/icon caches have different invalidation paths. For production readiness, do not let the service worker broad-cache arbitrary same-origin GETs; cache an explicit app-shell allowlist, bypass API/WebSocket paths, and cache only `response.ok` same-origin `basic` responses. For iOS Home Screen stale-version reports, first verify the exact live URL's HTML asset hashes and `/sw.js`/`/registerSW.js` headers; a CDN-cached bare `/sw.js` can keep iOS old even after Safari cache clearing. Prefer versioned SW registration (`/sw.js?v=<build>`) plus `updateViaCache: 'none'` and no-store/CDN no-store headers for app-shell control files. If installed PWAs white-screen before the React/Vue loading component, inspect whether the SW precaches/serves stale `index.html` and whether old hashed chunks are gone; when previous chunks cannot be recovered, use a missing-chunk rescue route rather than assuming `/releases/{releaseId}` exists. See `references/pwa-stale-index-missing-chunk-rescue.md`.
1a. **Advertising release folders that the server does not serve.** If `version.json` lists `/releases/{releaseId}/...` but nginx/object storage does not actually mount that path, rollback/old-bundle compatibility is fictional. Either retain and serve the full release asset directory, or emit root asset URLs and add a missing-old-chunk rescue path for `/assets/*.js`. See `references/pwa-stale-index-rescue-without-release-assets.md`.
1b. **Letting an old SW serve stale `index.html` after a deploy that removes old chunks.** If `dist/sw.js` precaches `index.html` and has a navigation fallback to it, an installed PWA can white-screen before React/Vue loading mounts. Do not precache HTML or runtime-cache app JS/CSS unless old hashed chunks are retained; verify the built SW, not only source config. See `references/pwa-stale-index-rescue-without-release-assets.md`.
1a. **Mistaking pre-React old-SW boot failure for a loading-screen bug.** If an installed iOS PWA shows white/blank after the native/static startup page but before React SplashScreen/loading appears, inspect the controlling SW and old chunk URLs first. A SW that precaches `index.html` and uses `NavigationRoute(createHandlerBoundToURL("index.html"))` can serve an old HTML shell whose hashed JS/CSS chunks no longer exist after deploy. Either stop using cached `index.html` as the online navigation fallback, or actually retain and serve `/releases/{releaseId}/...` assets with verified 200/hash readback. See `references/ios-pwa-old-sw-white-screen-before-loading.md`.
2. **Changing `?v=` and assuming iOS Home Screen icon updates.** Server freshness and OS icon cache freshness are separate.
3. **Prompting install before engagement.** It harms UX and Chrome may suppress future prompts after dismissal.
4. **Stacking safe-area padding.** One global custom property should drive all components.
5. **Using dark/mockup icon sources for production web assets.** Verify the source visually before generating every target size.
6. **Calling WebView packaging “native complete.”** Security and platform affordances still need explicit bridge/plugin work.
7. **Stopping at a static design/workflow gate when runtime placeholders remain unfilled.** If a PWA screen has placeholders such as “等待首帧”, `CONF --`, or `EVIDENCE --`, make them addressable `data-field`s and add a deterministic mock-controller smoke that proves the real start/capture path fills them. See `references/prd-stitch-pwa-self-circulation.md`.
- **Treating notification card time and event time as the same field.** For notification/message-center cards, the bottom-row/card timestamp should usually be delivery/creation time (`createdAt`) and list ordering should use raw `createdAt DESC`, not localized display text. Body-embedded business times (start time, expected release time, verification passed time) should be preserved separately as event/audit time (`occurredAt`) and only used as a tie-breaker or detail field. For incremental sync, only truly new notification IDs should be prepended; existing changed IDs (read-state/status/body updates) should be replaced in place so mutation events do not move old cards to the top. Add regressions for “existing unread item returns as read and ID order stays unchanged” plus “card display time follows createdAt while occurredAt remains the business time”.
- **Using `networkidle` for screenshots.** Long-polling apps may never become idle.
- **Letting overlays/toasts mask the acceptance surface.** If an install prompt, toast, splash, or banner covers the FlowNav/header while debugging mobile focus/layout, do not count the screenshot as proof. Dismiss or wait out the overlay, then measure the target header/title bounding rect and the app-level scroll owner (`scrollTop`, `overflow-y`) after focus. A visible content card under a toast can still mean the header was pushed above the viewport.
8. **Treating a Chrome tab screenshot as installed PWA proof.** `ChromeTabbedActivity` only proves browser behavior. Installed PWA/WebAPK evidence must show standalone/WebappActivity or the actual installed/native package content; if the launched installed package is stuck on Android default splash, record it as a wrapper/runtime blocker, not theme verification.
9. **Fixing route-return TabBar lift by changing the global gap.** If the lift appears only after navigation/update flows, avoid tuning `--tabbar-bottom-gap` or stacking `safe-bottom`; first add delayed route-return viewport resettling so stale visualViewport/window-scroll state cannot survive the route transition.
10. **Continuing to tune safe-area constants after repeated PWA TabBar failures.** If two or more gap/viewport changes trade one symptom for another, switch to render-ownership tracing: identify the root, app shell, scroll owner, and bottom chrome layer. A bottom TabBar clipped by a gray band can be an `absolute` chrome element inside an `overflow-hidden` app shell, but first prove whether the main content is also affected.
11. **Treating a missing bottom navigation screenshot as proof the component was deleted.** First classify browser vs installed PWA/WebView, then inspect whether the navigation DOM exists and is visible/inside the viewport. Compare local source/branch state against the served HTML asset hashes; stale service-worker/cache or a dirty stale worktree can mimic a code regression. For layout-only diagnosis, seed minimal auth and stub APIs so backend/login failures do not hide the chrome evidence.
11. **Letting top-fallback recovery become the normal TabBar positioning model.** If a fix introduces `--tabbar-top`, `--tabbar-bottom`, `data-tabbar-top-fallback`, or visualViewport recovery, keep the normal TabBar bottom-owned in CSS and enable top anchoring only when the measured TabBar rect is actually outside the visual viewport. Avoid JSX inline `style={{ top: ..., bottom: ... }}` as the default placement path; it lets simulator/standalone viewport drift hide the bar while DOM tests still pass. See `references/tabbar-top-fallback-regression.md`.
12. **Mistaking implemented routes for usable navigation.** In RN/mobile avatar shells, non-home surfaces can be technically reachable while the simulator still feels Home-only because controls are icon-only or every destination opens the same generic detail container. Add visible labels to Home navigation, strong page identity on each secondary surface, and an in-page tab/segmented switcher for direct cross-surface navigation. Verify with simulator screenshots after reinstall, not only Jest. See `references/rn-simulator-page-discoverability.md`.
13. **Stopping after bottom-owned recovery when installed PWA still clips bottom chrome.** If real PWA/WebView/simulator evidence still shows no bottom navigation after the DOM exists and bottom fallback was corrected, switch the normal placement model to a top anchor derived from measured app visual height minus chrome height and bottom gap. Preserve platform bottom-gap tokens, but avoid relying on CSS `bottom` inside clipped app shells. Add runtime reconciliation for the app visual-height token on every platform and verify with browser + standalone mobile harness. See `references/pwa-tabbar-top-anchor-visual-height.md`.
14. **Treating kill/reopen missing bottom chrome as another positioning bug without checking startup markers.** Applicability: installed PWA/WebView sessions with a splash/loading overlay that temporarily hides restored chrome. If the navigation DOM exists and its rect is inside the viewport, but computed opacity/pointer-events keep it invisible, inspect the root splash/loading marker before changing safe-area or top/bottom anchoring again. A splash component that reads a persisted “already shown” flag during render and writes it in a timer effect can rerender, cancel its own removal timer, and leave the marker permanently hiding bottom chrome. Freeze the per-mount splash-play decision in a ref and test the timer path. See `references/pwa-splash-marker-tabbar-restore.md`.
15. **Fixing a reported short loading page by hiding/loading bottom chrome first.** When the user says the loading page is short, measure root/splash/app-canvas height ownership separately from bottom-chrome visibility. Anti-condition: do not use “hide navigation during loading” as a substitute for proving whether `html`, `body`, app root, app canvas, and splash root match `visualViewport.height`.
16. **Confusing iOS splash shortness with normal-page safe-area downshift.** If the startup splash/loading surface looks like it is missing the status-bar/Dynamic-Island strip, inspect `apple-mobile-web-app-status-bar-style` and first-paint boot-script rewrites before changing page layout. `default` status-bar mode can make the WebView content area exclude the status bar, so `.splash-root { inset: 0 }` still cannot cover the missing strip; keep/restore `black-translucent` when the app must own a fullscreen splash. If the already-rendered page starts too low, diagnose `--safe-top`/TopBar/main insets separately instead. See `references/ios-pwa-splash-status-bar-viewport.md`.
17. **Fixing a tall bottom composer by tuning safe-area or padding first.** If a chat/support/assistant screen shows a large blank white input area, inspect flex ownership before safe-area constants: outer screen should be height-bounded, the message/list owner needs `min-h-0 flex-1 overflow-y-auto`, the composer should be `shrink-0`, and the textarea/input needs an explicit one-row base height with controlled auto-resize/reset. See `references/mobile-composer-flex-height.md`.
18. **Fixing keyboard-open composer/header loss by forcing window scroll first.** For mobile chat/support/assistant composer routes, the correct acceptance model is visual-viewport height ownership: keyboard shrink should shorten the route shell and middle activity region, not require `window.scrollTo(0,0)` while the textarea remains focused. Before adding fixed/z-index/scroll-reset patches, prove whether the shell consumes `visualViewport.height` and whether focused composer inputs are allowed to update the app visual-height token. See `references/mobile-composer-visual-viewport-shell.md`.
19. **Letting global top prompts mask composer-header acceptance.** On keyboard-sensitive chat/support/assistant composer routes, suppress or defer top install/update toasts while verifying the fixed header/FlowNav. A screenshot where the header is covered by a toast is not acceptance evidence. Add a route-scoped regression test for prompt suppression and keep ordinary non-composer routes unchanged.
17. **Fixing a bottom gray/blank band by changing bottom-chrome positioning before finding the scroll owner.** If the main content area also scrolls into or is covered by the band, enumerate computed `clientHeight/scrollHeight/scrollTop/overflow/padding-bottom` for root, app shell, intended scroll container, page root, and bottom chrome. A `padding-bottom` scroll reserve on the internal scroll owner can create a visible pure-padding tail exactly equal to chrome height plus bottom gap; fix that reserve model before moving chrome to `position: fixed`.
18. **Calling a fixed brand splash "first-screen loading" without measurement.** A React-mounted splash can start only after JS loads, then add its own fixed animation/fade duration on top of the actual content-ready time. Measure content-ready and user-visible-ready separately, and cap splash duration with a first-screen-ready signal instead of always playing a full 4-5s animation. See `references/ios-pwa-sw-cache-and-splash-measurement.md`.
19. **Creating a native startup image that does not match the accepted loading overlay.** iOS static startup, Android WebAPK launch inputs, and React SplashScreen are one startup system. The accepted standard may already be the existing React loading animation; in that case, do not redesign or replace the loading overlay just to fit a new static image. Generate iOS startup PNGs and Android manifest/icon inputs to match the existing loading first. Only change the React loading when the user explicitly approves a loading redesign. See `references/pwa-startup-splash-stitch-sdk.md`.
