## Key Patterns

### PWA cache/version strategy

- Treat `package.json.version` as the human release source.
- Inject a build number for service-worker cache names so each deploy invalidates Workbox runtime caches.
- Keep `skipWaiting` + `clientsClaim` on when immediate activation is desired.
- For finance/transaction PWAs where forced mid-flow reload is unsafe, use route-aware SW activation instead of relying on reinstall or a manual “clear cache” page: main/safe navigation surfaces can auto-apply `isUpdateAvailable` with `skipWaiting` + current-page reload, while sensitive/non-safe flows show an update toast/sheet with an immediate update action and block or defer risky submits until the user updates or returns to a safe route.
- Remember iOS icon caching is OS-level: `?v=` and redeploys can prove the server is correct without changing the Home Screen icon immediately.

### Silent release / OTA control-plane pattern

When the task is long-term silent client hot-update / OTA governance, do **not** reduce the answer to SSR, a version-update toast, or a single "latest version" config. Treat it as a release control-plane problem:

- Backend decides the user/platform/channel-specific release manifest; client executes preload, safe-boundary activation, rollback, and reporting.
- Admin release list is the governance surface for the full lifecycle; ordinary version dropdowns are insufficient for release selection because operators must compare status, asset completeness, API contract, health, and disabled reasons.
- For publish/rollback/override actions, prefer a modal/drawer with a candidate Release table filtered by `usage` over a dropdown. Show `selectable`, `recommended`, and `disabledReason` from the backend.
- Rollback interaction should include target selection, backend preview/impact analysis, reason type + required reason text, target `releaseId` re-entry, privileged confirmation/GA if available, append-only audit with before/after, and a post-rollback observation panel.
- Historical release assets should be versioned by `releaseId` under CDN/object storage; CDN is a distribution/cache layer, not the source of truth. Keep rollback targets and still-active releases from being garbage-collected.
- When the test environment uses Railway Docker deploys, do not treat container image replacement as the release artifact store. Generate a business `release-manifest.json` during app build, retain `/releases/{releaseId}/...` assets via Railway Volume or external object storage, and have the app/CI register the release with the backend. See `references/railway-client-release-cicd.md`.

### Offline context assistant / evidence-bound PWA companion

When a PWA is intended to act as an offline assistant companion, do not default to a local LLM as the first implementation. If accuracy and safety matter, treat offline mode as an evidence-bound context assistant: the online agent/server generates `ContextCard`/`EvidenceSpan`/task snapshot objects; the PWA stores them in IndexedDB; a Web Worker performs local retrieval, scoring, intent gating, and response assembly; sources are collapsed by default; insufficient evidence, current-fact questions, external actions, and high-risk requests become refusal/draft/handoff rather than fabricated answers. Keep WASM/WebGPU/local models as later rerank/compression enhancements after evaluation. See `references/pwa-offline-context-assistant.md`.

### Install UX

- Chrome/Edge can emit `beforeinstallprompt`; Safari iOS never does.
- Store the deferred event only after `e.preventDefault()` and consume it once.
- Treat `beforeinstallprompt.userChoice === 'accepted'` as “browser prompt accepted,” not final installation. Android OEM launchers such as OnePlus/ColorOS may still show a separate home-screen icon permission, and users can still end up with only a Chrome shortcut.
- For Android install copy, distinguish **generic user-facing guidance** from **OEM troubleshooting detail**:
  - Generic C-side banners/toasts, especially Pixel/Chrome fallback states, should stay concise: show the action as “查看步骤 / View steps”, then give browser-menu install guidance. Do **not** mention specific systems/OEMs, icon permissions, “desktop icon”, “shortcut”, OnePlus/ColorOS, or “Chrome creates shortcut” in the normal customer-facing copy.
  - Put OEM-specific launcher permission wording in troubleshooting/support docs or conditionally shown recovery flows only. If OnePlus/ColorOS then shows a system dialog worded “允许 Chrome 创建桌面快捷方式吗?”, the internal support guidance can explain that allowing it places the installed PWA icon. See `references/pwa-install-prompt.md`.
- For Android install copy, distinguish target families before writing user-visible guidance. Pixel/Google Chrome fallback copy should stay generic and action-led: show “查看步骤 / View steps”, tell the user to use the browser menu and choose the install option, and avoid concrete OEM/system/icon/shortcut wording such as “一加/ColorOS/鸿蒙/桌面图标/创建桌面快捷方式/浏览器快捷方式”. OEM-specific launcher-permission wording belongs only in an OEM-specific troubleshooting surface, not in the generic user toast. See `references/pwa-install-prompt.md`.
- Mark an app installed only from standalone-mode readback or a later runtime check after launch from the desktop icon; do not hide install UX solely because `userChoice` was accepted or because `appinstalled` fired. Treat `appinstalled` as “desktop entry created / install flow completed”, not proof of standalone WebAPK.
- When auditing an existing install implementation, inspect both the hook and its tests: tests may have encoded the wrong product model by expecting `isInstalled === true` after `userChoice.accepted` or `appinstalled`. Update the state model and regression tests together so intermediate Chromium signals remain distinct from `standaloneVerified`.
- For Android Chrome/Edge install UX, gate proactive install UI on the real `beforeinstallprompt` event. Do not show a timed “查看步骤 / View steps” fallback on mainstream Chrome just because no event arrived; keep it silent until browser readiness. Reserve timed manual guidance for Harmony/Huawei/OEM browsers that are known not to emit the event reliably. See `references/pwa-install-prompt.md`.
- Prompt after value commitment (login / first transaction / repeated visits), not on first paint.
- Provide explicit iOS Share → Add to Home Screen copy when no browser event exists.

### Safe-area and installed-mode layout

- `viewport-fit=cover` is required but not sufficient.
- Run standalone-only polyfills in `<head>` before CSS render if iOS reports zero safe-area values.
- Make `--safe-bottom` / `--safe-top` the single source of truth; avoid compounding constants across App, Screen, and TabBar.
- When H5/browser is correct but installed iOS/Android PWA spacing differs, derive platform/display-mode data attributes and feed TabBar through normalized app tokens (`--tabbar-bottom-gap`, `--tabbar-content-reserve`) rather than raw `env(safe-area-inset-bottom)`. When evidence shows Android needs the bottom safety height but iOS shows an extra blank strip, select static platform baselines: Android = system-nav safety baseline, iOS = 0. If browser mode is correct but installed standalone still leaves a blank band or clips the TabBar after the baseline fix, stop tuning gaps and trace the rendering ownership: app-shell height, overflow clipping, and whether the TabBar is absolute inside a clipped shell vs fixed viewport chrome. Avoid `100lvh` guesswork on iOS PWA; prefer binding the standalone shell to a fixed root or moving bottom chrome out of clipped content. See `references/pwa-standalone-tab-safe-area-normalization.md` and `references/pwa-tabbar-root-scroll-and-update.md`.
- When browser H5 shows a solid strip under a floating Liquid Glass TabBar, debug placement separately from glass styling: browser mode usually wants `--tabbar-bottom-gap: 0px`, while standalone mode can opt into a bounded safe-area gap. See `references/browser-h5-tabbar-safe-area-strip.md`.
- When a PWA TabBar gray/blank band affects the main content area too, inspect the internal scroll owner before changing chrome positioning. A full `padding-bottom: tabbar height + gap` reserve on `main[data-screen-scroll]` can create a real scrollable padding tail. Prefer ending the scroll viewport above the TabBar and retaining only a small visual-gap padding. See `references/pwa-tabbar-scroll-owner-debugging.md`.
- On Android installed PWAs, do **not** synthesize iPhone-style bottom inset from `screen.height - window.innerHeight`; that delta can include system chrome and lift the TabBar too high. See `references/android-pwa-safe-area-overoffset.md`.
- When Android PWA TabBar is too far above the visible bottom, separate TabBar height from TabBar position. Measure `nav.getBoundingClientRect().height`, computed `bottom`, `visualViewport.height - nav.bottom`, and the built CSS tokens. If Android standalone adds both a platform baseline (for example 32px) and a visual gap (for example 16px), and the app canvas is already trimmed, patch only `[data-display-mode="standalone"][data-platform="android"]` to lower the TabBar while leaving iOS/browser rules intact. See `references/android-pwa-tabbar-bottom-gap-regression.md`.
- If a device or test environment disagrees with local source, inspect the actual deployed CSS/JS assets and target branch (`git fetch`, compare test/staging/main, fetch built CSS URLs) before changing layout. A stale/test bundle can still contain additive Android tokens such as `--android-standalone-tabbar-safe-baseline + --tabbar-visual-bottom-gap`, lifting the TabBar even when current source has `--tabbar-bottom-gap: 0px`.
- On Android installed PWAs, do **not** synthesize iPhone-style bottom inset from `screen.height - window.innerHeight`; that delta can include system chrome and lift the TabBar too high. See `references/android-pwa-safe-area-overoffset.md`.
- If Android screenshots show the TabBar clipped by a black system navigation bar instead of floating too high, treat it as the opposite underlap class: measure a narrow Android-only visual bottom obstruction with `visualViewport`, keep it in a separate token, and do not write it to generic `--safe-bottom` or iOS fallbacks. See `references/android-pwa-system-nav-underlap.md`.
- If the screenshot also shows a black or mismatched **top** status bar, split the task into two acceptance atoms before coding: system-bar theming/ownership (meta `theme-color`, manifest `theme_color`, WebAPK cache, or native WebView status/navigation bar config) and bottom viewport underlap. Web CSS/layout can fix bottom in-page chrome, but a native/WebAPK system-bar color problem may require manifest freshness, reinstall/cache validation, or native shell settings. See `references/android-pwa-system-bars-theme-and-viewport.md`.
| Android standalone PWA/WebAPK bottom sheets, full-screen portals, scroll containers, and bottom chrome all extend into the gesture/navigation area while iOS standalone is correct, diagnose the app canvas/root shell before changing TabBar or BottomSheet gaps. Look for recent `100dvh`/`100vh`/`100lvh` and fixed-root changes; preserve iOS fullscreen fixes and apply a narrow Android-only canvas trim when the Android canvas is too tall. If a canvas trim is active, do not also lift TabBar/BottomSheet with Android bottom gaps; separate canvas trim, chrome placement, and content reserve. See `references/android-pwa-app-canvas-bottom-trim.md` and `references/android-pwa-canvas-trim-and-bottom-chrome.md`. |
- When fixing Android PWA/WebView dark-mode system bars, preserve the product theme model. Do **not** remove a “Follow system” option just to stop OS dark mode from overriding fixed themes. Preferred controlled model: fixed `light`/`dark` choices never read OS color-scheme; explicit `system` is the only path that reads `prefers-color-scheme`, listens for changes, and updates `data-theme` plus a single non-media-bound `theme-color` tag.
- Scope: class-level mobile web / installed web-app flow pages. Applicability: iOS keyboard opens on an editable field and the fixed app canvas or flow header shifts out of view, while Android/desktop should remain unchanged. Anti-conditions: do not apply this to Android system-navigation inset bugs, and do not move global safe-area constants before proving the bug occurs only during focused editable states. Pattern: gate on iOS platform marker + focused editable + `visualViewport` shrink, write an iOS-only keyboard inset token, add content/scroll reserve to the app-owned flow scroller, clear the token on blur/viewport recovery, and regression-test that Android/browser/blurred states stay zero. Real-device iOS browser/installed-mode evidence is required before UI acceptance.
- When a stale installed web app may keep old client code after lock/unlock, app background/foreground, browser-tab switching, or a long no-user-action idle window, add quiet service-worker update checks on `visibilitychange`, `focus`, `pageshow`, and activity-reset idle timers (`pointerdown`/`keydown`/`touchstart`). Separate download from activation: `registration.update()` may silently fetch a new SW/resources, but current JS changes only after reload. Prefer safe-boundary auto-activation on main/non-sensitive routes with visible document and no dirty form; otherwise show the existing update toast/prompt rather than forcing reload mid-transaction. Name the UI by its actual component behavior (toast vs banner/bar). See `references/pwa-silent-safe-update-boundaries.md`.
- When adding mobile/PWA lifecycle coordination for foreground/background/offline recovery, keep app-update, heartbeat, business sync, and realtime channels as separate lanes. On hidden/background/offline, stop polling and disconnect realtime reconnect loops; on visible/foreground/online, run REST compensation sync first, then reconnect realtime and resume polling. If a planned heartbeat endpoint is not deployed, keep the client call feature-flagged off by default. If business API success offsets explicit heartbeat, emit only minimal activity state such as `{ at }` from any global event, never URL/method/query details; exclude the heartbeat endpoint itself so heartbeat does not suppress later heartbeat. Guard async heartbeat timers with a disposed flag and debounce/in-flight foreground resume because `visibilitychange`, `focus`, and `online` often fire together.
- When foreground/background lifecycle work also touches notification sync, realtime connections, and user-online heartbeat, avoid adding independent timers in several hooks. Centralize lifecycle inputs, pause polling and SSE/WebSocket in hidden/offline states, run REST cursor repair sync before reconnect on resume, and keep heartbeat feature-flagged until the backend endpoint exists. For notification mutation sync, replace existing rows in place; only genuinely new notification IDs should prepend. Card/list timestamps should use delivery/creation time (`createdAt`) when product expectation is “latest received first”, while business event time (`occurredAt` or embedded body times) remains detail/audit metadata. See `references/uvisa-c-lifecycle-and-notification-sync.md`.
- When a floating TabBar is correct on first render but becomes lifted after routing back from About/update/legal/settings screens, suspect delayed PWA viewport settlement rather than immediately changing TabBar CSS constants. Add a route-return multi-pass settle (`immediate`, `requestAnimationFrame`, and short delayed passes such as 150/300/600ms) that resets stray window scroll and reconciles safe-area / visual-inset tokens. See `references/pwa-route-safe-area-resettling.md`.
- Applicability: mobile/PWA SPAs whose CSS root-lock or viewport-height rules depend on `data-platform` / `data-display-mode`. Anti-condition: apps whose server markup already includes these stable markers. If outer roots or the full-screen app shell show scroll only during splash/loading before the JS bundle initializes, seed the markers in a head inline script before the module bundle and verify during splash that outer layers have no scroll overflow. See `references/pwa-first-paint-layout-markers.md`.

### Icon, splash, and installed app labels

- Map native source packages to web targets intentionally: iOS 180 for apple-touch-icon, Android playstore 512 for manifest/maskable, high-res source for favicons.
- Strip SVG shadows, filters, and decorative strokes from production favicon/mask assets.
- Verify dimensions and hashes after generation, especially when design packages contain multiple visual variants.
- In-app identity icon reuse (scope: class-level PWA/mobile-web; applicability: About/settings/app-info/splash surfaces that are intended to match the installed icon; anti-condition: skip when product intentionally uses a different in-app mark): inspect the current app's manifest/apple-touch icon source and cache-bust query, then render that asset directly instead of recreating a similar JSX/CSS badge. Keep the change scoped to the surface and add a regression assertion for the rendered image `src`.
- When changing the installed PWA/home-screen app name, update every install-label surface together: web manifest `name` and `short_name`, `<meta name="application-name">`, `<meta name="apple-mobile-web-app-title">`, and any native-shell config such as Capacitor `appName`. Keep browser `<title>` and in-app brand copy unchanged unless the request explicitly asks for those too.
- Verify the built artifact, not only source: parse `dist/manifest.webmanifest` for `name`/`short_name`, inspect `dist/index.html` for app-name meta tags, and run the normal build gate before committing.

### Offline context assistant / hybrid avatar positioning pattern

When a PWA/mobile assistant needs offline usefulness, prefer an evidence-constrained context assistant over a free-running local LLM. Online Hermes/server should generate compact `ContextCard` / `EvidenceSpan` records; the PWA stores them in IndexedDB, retrieves/reranks in a WebWorker, and uses an evidence gate to choose answer / cautious answer / refusal / draft-only. Show sources collapsed by default, and send low-confidence/refused/action requests as handoff packets for online reconciliation. Keep current facts, tools, and external side effects online-only. See `references/pwa-offline-context-assistant.md`.

For mobile “avatar/clone/companion” products, do not let offline capability become the product’s primary positioning unless the user explicitly chose that strategy. Default product model: hybrid/online authority first; local evidence and local models are fallback lanes for offline or weak-network conditions. UI copy should say “hybrid”, “online Hermes/Gateway authority”, and “local evidence fallback/兜底” rather than implying the phone is an always-primary “offline AI” or that the local model is the fact source. If the user corrects this positioning, patch both implementation copy and canonical docs/profile so screenshots, tests, and SSOT all agree.

For production-facing offline/hybrid assistant projects, do not stop at a shared core package or gateway contract. A basic app shell is part of the first usable slice: manifest/standalone metadata, service worker that caches app-shell assets only, truthful runtime status (`Local/Hybrid/Online` or `Fallback Local/Hybrid/Online`), composer, evidence/source panel, queue indicator, permission boundary copy, and a browser smoke where a real query produces a local answer/refusal/draft state. Gateway dry-run and persistence can be later ratchet steps, but the UI must truthfully show what is and is not wired.

### Hybrid WebView packaging

- When PWA/RN/Desktop/Web-UI are multiple entries into the same product, create a shared entry/readiness contract before adding more screen-level branching. Keep desktop/web-ui as governed operator entries, PWA/RN as mobile companion entries, and make the authority chain explicit in a small shared package. The package should expose navigation/readiness metadata only; it must not become another fact source. See `references/multi-end-entry-core.md`.
- After the entry/readiness contract exists, do not stop at static UI. Wire the first real projection lifecycle slice: bootstrap before changes, derive readiness from actual cards/spans, persist RN/PWA projection as local read-only evidence, and keep empty/unreachable Gateway states non-verified. See `references/mobile-projection-bootstrap-readiness.md`.
- When a PWA must remain compatible with a future React Native/iOS shell, do not fork the offline assistant/business logic into separate web and native copies. First extract a pure TypeScript shared core with tests, make the PWA consume it, then add a native-shell preparation package with runtime/model/signing validators. Generate the Xcode/RN project only after Bundle ID, signing mode/Team ID, runtime choice, model packaging, and distribution path are confirmed.
- Prefer Capacitor when the existing SPA is clean, team is web-focused, and native requirements are moderate.
- Intercept native back button and route through the SPA router; otherwise system back/side-swipe can exit the app.
- For primary TabBar routes, explicitly decide terminal-route behavior. If Home/Card/Wealth/Me should behave like app roots, check the route predicate before `window.history.length` and call `CapacitorApp.exitApp()`; don't let Android Back resurrect prior flow pages just because browser history exists. See `references/native-back-button-terminal-tabs.md`.
- Plan native/security gaps explicitly: biometrics, push, SSL pinning, secure keyboard, jailbreak/root detection.

### Screenshot verification

- Use an existing Chrome profile when production auth is required.
- Run Playwright from a project with `@playwright/test` installed.
- Prefer `domcontentloaded` plus a bounded render wait over `networkidle` for production SPAs with polling/SSE.
- Always check whether the page redirected to login before treating screenshots as authenticated evidence.
- For local UI verification that must hit an online backend, use same-origin Vite proxy (`VITE_DEV_API_PROXY_TARGET=...` with runtime API base still `/api`) instead of setting `VITE_API_BASE` to the online URL. Start with `--strictPort`, kill stale listeners first, and verify both transformed `api.ts` and a proxied `/api/...` request. See `references/vite-proxy-online-backend.md`.
- For release-control screenshots, distinguish authenticated UI render from backend state evidence. Before claiming end-to-end success, probe the exact deployed API endpoints and confirm write/read-back; if the dev proxy points at a backend that lacks the new API, report the structured not-found response instead of mocking data. See `references/release-control-plane-real-verification.md`.
- For mobile focus/layout verification behind a branded startup animation, do not validate the target page while the splash/loading overlay is still visible. First wait for the real splash lifecycle to finish (`.splash-root` detached / `data-splash-visible` absent) unless the task is specifically about splash itself, then focus the input and measure header/composer rects. If waiting times out with `.splash-root.is-out` still mounted, treat that as a splash teardown bug, not as proof that the target page header is missing.

### Shared visual-component copy changes

When a mobile/PWA UI task asks to remove, rename, or hide text on a reusable visual component (for example a card face, account tile, banner, bottom action, or detail header), treat the component as the acceptance surface, not only the screenshot route:

1. Locate the reusable component and all route-level consumers before editing.
2. Add a negative regression test at the component level (`queryByText(...)` is null for removed copy) so every consumer inherits the behavior.
3. Keep adjacent non-target visuals intact (icons, status, amount, masked identifiers, spacing intent) unless the task explicitly asks to remove them.
4. Run both the component test and at least one representative route/detail-screen test that depends on the shared component, then run the build gate.
5. In closeout, state which consumers are covered by reuse and which still need live UI evidence before final Lark/production completion.

### Prototype restoration must include semantic routing

When restoring a mobile screen to match a prototype, do not stop at visual parity. Check every card/CTA against the product/PRD content source that defines its meaning:

1. Verify visible labels, links, and destination routes together. A card that visually says “AI assistant” but routes to human chat is a bug even if the screenshot looks correct.
2. If the product has split content sources (for example a full knowledge base vs a curated FAQ), map each UI entry to the right source and route: assistant/search surfaces should use the full knowledge base; FAQ surfaces should use curated FAQ entries.
3. Add route-level regression assertions for key links (`getByRole('link', { name: /.../ })` + `href`) alongside visual/text assertions.
4. Preserve intentionally requested deviations from the prototype (such as removing a contact channel) and state them explicitly in closeout so they are not mistaken for missed parity.
