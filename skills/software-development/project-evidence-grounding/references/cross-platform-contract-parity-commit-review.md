# Cross-Platform Contract-Parity Commit Review

## Applicability

Use when a target client (web/H5, iOS, desktop, or a rewritten mobile surface) claims behavioral parity with a reference client, especially across a sequence of commits involving navigation payloads, authentication gates, favorites, selectors, or state transitions.

Anti-conditions:

- Do not use commit messages, plan text, or evidence JSON as the behavioral authority.
- Do not require identical UI architecture when the target has a deliberately different but explicitly accepted interaction model; verify observable equivalence instead.
- Do not treat project-specific paths, branch names, IDs, or URLs from one audit as reusable defaults.

## Truth chain

For every parity claim, trace the complete source-to-sink chain:

1. **Reference producer** — click handler, intent/event creation, route builder, API call, or state transition.
2. **Reference payload** — exact field names, casing, identity fields, defaults, and authentication preconditions.
3. **Reference consumer** — receiver/page/controller that reads the payload and changes observable state.
4. **Target producer** — corresponding route, callback, request, or store mutation.
5. **Target consumer** — code that actually reads the forwarded value and renders/mutates the equivalent state.
6. **Observable proof** — runtime URL/API/UI/log evidence proving the effect, not merely transport.
7. **Negative proof** — forbidden mutation, anonymous request, fallback, stale identity, or hidden control does not occur.

A field copied into a URL, intent, event, or store is **transport parity only**. It is not behavioral parity until the target consumer reads it and produces an accepted observable effect.

## Commit-by-commit procedure

1. Pin the exact reference revision and each target commit hash.
2. Read each target commit with its parent diff; do not review only final `HEAD`, because later commits may mask or repair an earlier defect.
3. Build a compact matrix per commit:

   | Claim | Reference producer/consumer | Target producer/consumer | Runtime proof | Verdict |
   |---|---|---|---|---|
   | identity propagation | ... | ... | ... | pass/fail |
   | state/side selection | ... | ... | ... | pass/fail |
   | auth boundary | ... | ... | ... | pass/fail |
   | negative case | ... | ... | ... | pass/fail |

4. Distinguish three outcomes:
   - **APPROVE** — behavior and required negative cases are proved.
   - **AMEND** — a material source-to-sink or evidence gap exists; name the smallest required change.
   - **EVIDENCE GAP** — code is plausibly correct but an authorized runtime path (for example authenticated mutation) was not exercised. Do not mislabel this as a code defect.
5. Validate evidence packets against code. A `PASS` label is advisory; inspect what was actually measured. URL equality does not prove destination-state consumption, and a screenshot does not prove request identity.
6. Run fresh deterministic checks tied to the immutable commits where possible (`git show --check`, focused lint/tests/build) and state what they do not prove.

## Moving-worktree and read-only-build guard

A read-only review can overlap with another agent or developer editing or committing to the same branch. Build tools can also mutate tracked generated artifacts even when the reviewer intends no writes.

1. Capture repository status, branch, and exact `HEAD` before inspection; pin the requested hashes and their parent chain.
2. Base verdicts on immutable objects (`git show <hash>`, `git show <hash>:<path>`, `git diff <base>..<target>`, `git blame <target> -L ...`), not the moving worktree. Cite evidence as `path@<commit>:lines` so later commits cannot move the target.
3. Re-read `HEAD`, log/reflog, and status after every long-running build/test and before closure. If `HEAD` advanced, inspect `<target>..HEAD`, exclude later commits from the verdict, and state whether they overlap reviewed hunks.
4. Treat build commands as potentially mutating. PWA/Workbox/Vite and similar builds may rewrite tracked service-worker maps, manifests, or generated bundles. Snapshot status before the command; afterward inspect each new diff and restore only files proven to have been generated by that command. Never use broad reset/clean/checkout against a shared dirty repo.
5. If a build ran after `HEAD` advanced, bind the claim narrowly: it covers the requested code only when the later diff does not modify or repair the reviewed paths/hunks. Otherwise report exact-target build verification as unavailable.
6. When targeted lint fails, blame each reported line against the pinned target. Older blamed lines are baseline debt; findings introduced by the named commits remain blockers.
7. Finish with fresh status readback in every inspected repo and report pre-existing dirt separately from review-created artifacts.

A clean status observed earlier is stale evidence after later tool execution; never repeat it as the final state without fresh readback. Cleanup must not erase unrelated concurrent work.

## Renderer-state verification for chart/editor/map adapters

For parity work mediated by a third-party renderer (charting, rich-text editor, map, canvas/WebGL, diagram engine), treat framework state, ARIA state, and `data-*` mirrors as **intent evidence only**. They do not prove that the renderer accepted the command or placed the result in the correct internal surface.

1. Read the exact installed dependency version and its type/runtime implementation for ambiguous arguments such as `stack`, `overlay`, `pane`, `layer`, or `series`. Do not infer semantics from parameter names. A stacking flag may control behavior inside a newly-created pane rather than attach content to the main pane.
2. Trace target state through the adapter call into the dependency's actual consumer. Verify required destination identifiers (main pane/layer/axis/source) are supplied explicitly.
3. Probe renderer state where supported: enumerate panes/series/layers/indicators, inspect returned IDs, or expose a test-only readback from the real renderer API. Avoid assertions that merely reread state written by the application itself.
4. Add visual evidence that distinguishes placement, not just selection: an overlay must visibly occupy the reference surface; an independent pane/layer is a parity failure even when the selector says it is active.
5. Exercise teardown and recreation boundaries—theme changes, fullscreen/remount, symbol/data-source switches, and imperative reinitialization—and prove fixed/default layers plus current selections are restored after every rebuild.
6. When a harness only clicks controls and reads `aria-pressed`/`data-*`, classify it as control-state coverage, not renderer-effect coverage, and AMEND any stronger evidence claim.

## Preference-persistence parity probes

For settings such as chart periods, filters, tabs, display modes, or sort order, verify persistence as an observable state machine rather than only checking the storage write:

1. Start from a missing preference and confirm the documented default.
2. Select a supported non-default value, remount/reload the target, and confirm both the selected control and downstream consumer use the restored value.
3. Inject or otherwise exercise an invalid/unsupported value when the harness allows it; confirm the safe fallback. If runtime injection is unavailable, cite the exact validation branch and label that negative case static-only.
4. Exercise adjacent pseudo-options such as depth view, “all,” or transient modes. Determine whether they are part of the persisted preference or a separate state axis.
5. When the reference uses two keys/flags (for example, last real chart period plus current depth-view mode), do not collapse them silently. State whether the target intentionally persists only the durable preference, persists both axes, or has a parity gap.

A useful deterministic sequence is: default → choose non-default → reload → choose adjacent transient mode → reload. This distinguishes “last durable choice was preserved” from “current mode was fully restored.”

## Reference-defect and accepted-improvement rule

Reference clients can contain observable bugs such as switch fall-through, stale aliases, inconsistent defaults, or invalid-value acceptance. Do not require the target to reproduce a defect merely for byte-for-byte parity.

1. Prove the defect from the immutable reference revision and distinguish implementation behavior from likely contract intent.
2. Check whether product acceptance explicitly requires bug-for-bug compatibility. Without that requirement, a safer/correct target behavior may be an accepted improvement rather than an AMEND.
3. Report the divergence explicitly in the verdict so “parity” is not overstated.
4. If the divergence affects externally relied-on behavior, migration compatibility, persisted data, or cross-device continuity, fail closed and request an explicit accepted-equivalence decision.
5. Prefer a small target test or documented exception over copying the reference defect.

## Common parity traps

1. **Transport-without-consumption:** source and target both carry a field, but the target destination never reads it.
2. **Identity ambiguity:** several identifiers are accepted with an OR predicate, so list order can override the intended priority when fields disagree. Define precedence or reject inconsistent payloads.
3. **Anonymous-path-only proof:** login redirection is verified, but authenticated mutation is not. Usually classify as an evidence gap unless code inspection finds a defect.
4. **Final-HEAD masking:** later commits make the final tree pass while an earlier commit remains independently invalid.
5. **Evidence self-certification:** generated evidence says `PASS` but tests only route shape, control state, or application-owned mirror attributes—not the destination consumer or renderer effect.
6. **Architecture conflation:** reference uses a selected buy/sell tab while target shows both forms. Require an explicit accepted-equivalence rule; otherwise the parameter may be semantically inert.
7. **Renderer-argument folklore:** assuming flags such as `stack=true` imply main-surface overlay without reading the installed library implementation. Require explicit destination-pane/layer evidence.
8. **Reinitialization state loss:** a theme/fullscreen/remount path disposes the renderer after selections were applied, leaving control state active while fixed/default and selected renderer layers are absent.

## Concise verdict format

```text
<hash> — APPROVE | AMEND
- Reference behavior: producer -> consumer -> observable effect
- Target behavior: producer -> consumer -> proof
- Required amendment or remaining evidence boundary
```

Keep the final answer commit-by-commit and concise; move detailed matrices to an evidence artifact when needed.
