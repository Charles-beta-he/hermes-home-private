# Projectizing Extension Directions from Prototype/Console Evidence

Use this reference when a user says earlier expansion directions, long-term self-extension ideas, console dashboards, prototype folders, or capability panels should become durable projects.

## Trigger

- User references prior “扩展方向 / 长期自扩展 / capability directions / console project / roadmap”.
- Evidence lives in a local prototype, dashboard JSON, fallback UI data, plan doc, or mission ledger rather than a formal project profile.
- The task is portfolio governance, not direct feature implementation.

## Procedure

1. **Locate evidence without editing source code.** Inspect docs, dashboard snapshots, package metadata, and source constants that list directions. Treat generated dashboards and fallback UI arrays as evidence sources, not as canonical completion proof.
2. **Classify each direction:**
   - durable project: has independent objective, lifecycle, SSOT, ledger, gates, and recurring governance;
   - shared module/capability family: cuts across existing projects and should not duplicate a control plane;
   - relation-only: project facts/authority differ, only patterns transfer;
   - proposal only: useful signal but no proof/artifacts yet.
3. **Avoid duplicate governance surfaces.** If an apparent direction is already covered by `hermes`, `project-portfolio-os`, `hermes-skill-learning`, or another active project, register it as a shared module or relation instead of creating a new project.
4. **Create project metadata only by default.** For accepted durable projects, create/update profile, SSOT root, `progress-ledger.md`, relation entries, and registry rows. Do not modify the prototype/product source unless separately authorized.
5. **Preserve maturity truth.** Initial metadata can be `profiled/ledgered`; implementation components remain `proposal/needs-evidence`, `source-observed/needs-current-run`, or `validated-source-observed` unless current tests/readback prove more.
6. **Verify portfolio closure.** Run/read back the portfolio doctor/verify surface after registry/profile updates.

## Classification examples from the console session

- `hermes-self-extension-os`: durable project. Evidence: mission direction for long-term Hermes self-extension and human handoff loop. Type: `agent-runtime-evolution / mission-control-plane`.
- `hermes-control-console`: durable project. Evidence: local console long-term plan, dashboard snapshot, package scripts. Type: `operator-console`.
- `career-ops`: durable project candidate if user wants recurring JD/resume/story-bank/tracker work; starts as `proposal/needs-evidence`.
- `agent-governance`: usually not a separate project if already covered by Hermes platform, self-extension OS, portfolio OS, and skill-learning. Treat as shared module/capability family unless new independent SSOT/lifecycle emerges.

## Anti-conditions

- Do not turn every UI card or dashboard row into a project.
- Do not mark source-observed capabilities as validated runtime capability without current runnable proof.
- Do not merge product/business facts, auth state, secrets, mission budgets, or protected project code into a new project.
- Do not create task/session-progress skills from a one-off projectization pass.
