# Human Inbox execution-flow gate triage

Use when the control console Human Inbox shows `暂停`, `Execution Flow Gate`, or long task-file cards from `execution-flow-dry-run`.

## Source boundary

- Human Inbox entries in the standalone control console are projected from `approvalRequests` in `public/hermes-dashboard.json`.
- Those requests are generated by `scripts/generate_hermes_dashboard.py` from `brain_task_orchestrator.py execution-flow-dry-run --json`.
- Treat Brain task markdown as the lifecycle SSOT; Human Inbox is an operator decision projection, not a lifecycle source.

## Triage sequence

1. Refresh the snapshot with the console repo's snapshot command, then inspect `approvalRequests`.
2. Classify each request by status and blocker:
   - `status in {done, archived, cancelled, completed}`: terminal row; should not appear in Human Inbox.
   - `blocker=execution_flow:external_side_effect`: real authority/side-effect gate; do not auto-continue.
   - `blocker=execution_flow:evidence`: evidence gap; can usually be routed to repair with required evidence.
3. For terminal rows, fix the projection generator rather than mutating task files: filter terminal statuses/stages out of `approval_requests_from_execution_flow()` and add a UI contract regression test.
4. For real external-side-effect gates, keep `暂停` unless the user explicitly authorizes the writeback/budget/permission boundary.
5. For evidence gaps, list the exact missing evidence and only proceed with deterministic proof collection/readback.

## UI/product rule

Human Inbox cards should show only active human decisions. Do not show `完成 · ... · 暂停` cards; they create false work. Terminal execution-flow rows may remain in technical audit data, but not in the first-level Human Inbox action queue.

## Regression checks

- `pnpm test:ui`
- `pnpm build`
- `pnpm snapshot`
- Browser/DOM readback: Human Inbox has no terminal rows; `done_count == 0`; remaining cards are active `blocked`/`retry` decisions.
